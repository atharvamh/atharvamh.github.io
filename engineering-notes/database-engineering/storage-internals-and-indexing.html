How a table's rows actually sit on disk, why B+Trees won out over every other search tree, and why a single choice of primary key can make or break write throughput.

Module III — Storage Internals

s9. Table & Heap Internals (Pages & Row IDs)

A relational table is a logical abstraction. Underneath, the DBMS represents it as a collection of physical files on disk. To read, write, and index that data efficiently, the engine segments those files into fixed-size blocks called pages, and organizes rows inside structures called heaps.

📦 The Core Elements of Storage Architecture

1. The Page / Block — the I/O atom

A page (or block) is the atomic unit of database disk I/O. Databases never read or write individual rows from a drive — they retrieve and commit entire pages containing those rows, typically 8 KB in PostgreSQL and 16 KB in MySQL InnoDB. Even a single-row index lookup pulls the whole physical page into the buffer pool first.

2. Heap storage vs. index-organized tables

A heap is an unordered collection of pages, where rows are written wherever free space happens to exist — physical sort order is ignored entirely. PostgreSQL tables are strict heaps. InnoDB tables, by contrast, are index-organized (clustered indexes): rows are physically ordered and stored directly inside the primary key's leaf nodes.

3. Physical row IDs — ctid, TID, DB_ROW_ID

Every row has an internal physical address — the row ID — represented as a coordinate: (page number, tuple slot offset). A Postgres ctid of (4, 12) means "go to page 4, read the 12th row pointer." Indexes store these physical row IDs as leaf values, to locate raw rows in the heap.

THE ROW MIGRATION PROBLEM (WRITE AMPLIFICATION)

Update a variable-length field — say, 'Bob' grows into a much longer string — and the row expands. If its page is already full, the row no longer fits in its original slot.

The risk: if the engine physically migrates the row to a new page, every index entry that points to its old physical coordinate breaks, forcing an expensive rewrite across every index.

The indirection layer: slotted page architecture

Modern engines protect against this with a slotted page layout inside every block:

  • Page header — metadata: page offsets, free-space pointer, transaction boundaries.
  • Line pointer array (slot array) — grows forward from just after the header. Each entry is a lightweight pointer to a row's actual byte offset.
  • Tuple payloads — the row byte arrays themselves, written backward from the end of the page.
ENGINEERING NOTE

Because of this indirection, if Row B is updated and shrinks or relocates inside the same page, only its Slot 1 offset needs updating. External index maps that reference (Page, Slot 1) remain completely valid and untouched.

s10. B-Tree & B+Tree Indexing Internals

Querying a table with no index forces a full table scan — every page gets pulled into memory, and disk I/O becomes the bottleneck. Indexes solve this by building a structured routing table. In transactional systems, the standard implementation is the B+Tree.

Why Not a Binary Search Tree?

The reasons databases avoid plain BSTs or red-black trees are purely physical:

  • Tree depth & disk spanning — a BST branches at most 2 ways. Indexing 1,000,000 rows needs log₂ 1,000,000 ≈ 20 levels. Since each parent-child link can point to a completely different disk page, finding one key could mean 20 random disk reads.
  • No page alignment — a BST node holds just one key and two child pointers, wasting almost all of an 8 KB page's capacity and fragmenting memory badly.

The Solution: Shallow Depth, High Fan-Out

A B+Tree is a self-balancing tree built around large, page-aligned blocks, using two distinct node types:

  • Internal nodes (routing guides) — hold only search keys and child pointers, no row data at all. This maximizes fan-out: a routing page holding 500 keys gives a branching factor of B = 500.
  • Leaf nodes (data anchors) — hold the actual index key values, paired with physical row IDs (or, in a clustered InnoDB table, the full row itself).

Since every payload lives in the leaves, internal nodes stay light and fan-out stays huge. A B+Tree with B = 500 can index millions of keys in just 3 levels — capping physical page lookups at 3 hops.

B-Tree vs. B+Tree

STANDARD B-TREE

Stores records in both internal and leaf nodes. That leaves far less room for routing keys per internal node, so the tree grows deeper and needs more disk reads. Range queries are slow too — the engine must traverse up and down between nodes.

MODERN B+TREE

Keeps data exclusively in leaves, and links every leaf together sequentially via a doubly-linked list. A range scan (WHERE balance > 100) walks down once to find the start, then scans sideways through linked leaves — no further tree traversal needed.

s11. Clustered vs. Heap Tables

A critical fork in physical storage design is the choice between heap-based storage (PostgreSQL's native model) and clustered indexes / index-organized tables (MySQL InnoDB's native model). Your primary key's data type — auto-incrementing integer vs. random UUID — has completely opposite performance implications depending on which model you're on.

📌 Direct Lookup vs. Double Lookup

The Random UUID Clustered-Index Trap

THE PROBLEM

Insert rows with a fully random primary key (UUIDv4) into an InnoDB table, and three things go wrong at once:

  • Continuous page splits — an unsorted key lands mid-page. If that 16 KB page is full, the engine must split it, moving half its rows to a new page.
  • Heavy random writes — instead of appending sequentially, the engine reads random uncached pages into RAM, writes, and flushes back — causing disk-head thrashing.
  • Bloated secondary indexes — since InnoDB secondary indexes store the PK value at leaf level, a 36-character UUID primary key makes every secondary index far larger.

The Fix: Sequential Keys & Postgres's Natural Immunity

  • Sequential keys for clustered tables — use auto-incrementing integers, or a sortable format like UUIDv7 (which embeds a millisecond timestamp at the front). New rows land sequentially at the end of the tree, and page splits disappear.
  • PostgreSQL's heap-append advantage — since Postgres is heap-based, a random UUID insert just appends to the active page — fast regardless of key order. The primary key's own B+Tree index can still split, but because its leaves only store a light 6-byte ctid (not the whole row), those splits are far cheaper than InnoDB's table-page splits.

Why InnoDB Pays the Double-Lookup Cost

POSTGRES DIRECT PATHWAY

secondary index → ctid → direct page read. Fast single-hop reads. But if a row's physical location changes, every secondary index needs its ctid updated.

INNODB DOUBLE-LOOKUP PATHWAY

secondary index → PK value → clustered B+Tree traversal → row. If a row moves during a page split, secondary indexes don't break — they point at a logical key, not a physical address. The cost: every secondary lookup pays for two tree traversals.

s12. Row vs. Columnar Storage (OLTP vs. OLAP)

A table is logically a two-dimensional grid, but physical storage — SSD or HDD — is a strictly one-dimensional array of bytes. Serializing a table onto that array means choosing an orientation: row-oriented (built for transactions) or columnar (built for analytics).

The Core Structural Difference

  • Row-oriented (OLTP) — one page holds several complete rows; every column of a given row sits contiguously: [Row1: A,B,C][Row2: A,B,C].
  • Columnar (OLAP) — one page holds one column across thousands of rows: Page A: [Row1.A, Row2.A, Row3.A], Page B: [Row1.B, Row2.B, Row3.B].

OLAP on Row-Oriented: the I/O Bottleneck

Run a warehousing query — an aggregate, an average, a group-by — against a row-oriented OLTP database, and performance degrades badly:

  • Massive I/O waste — averaging one column across 50,000,000 rows still pulls every column (IDs, descriptions, timestamps) into the buffer pool. Most of those bytes are discarded instantly.
  • Buffer pool pollution — loading heavy rows to scan one column evicts valuable transactional pages from RAM, slowing down unrelated queries too.

OLAP on Columnar: the Cure

  • Direct sector sweeps — querying a single column means the engine reads only that column's file, sequentially. Every other column stays untouched.
  • Heavy compression — a page filled with one data type compresses extremely well. Run-length encoding ([100,100,100] → 3x100) or delta encoding can shrink storage by up to 90%.

The Columnar Penalty

ROW RECONSTRUCTION & WRITE COST

SELECT * FROM users WHERE id = 42 forces the engine to open a separate file per column, read slot 42 in each, and stitch the row back together in RAM — heavy random-seek latency. Inserting or updating one row means touching dozens of separate column files at once.

The OLTP Answer: Continuous Append

To sustain high-throughput concurrent writes, OLTP engines keep every row's columns bundled together in one page — one atomic append per insert, and a point lookup lands directly on a slotted page where every column is already sitting side by side.

The Workload Divide

MetricRow-oriented (OLTP)Columnar (OLAP)
