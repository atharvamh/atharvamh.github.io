Database Engineering Notes

ACID, Transactions & Concurrency

How a database keeps its promises when things crash, and how it keeps those promises without making every transaction wait in line.

Module I — Transactions & ACID

s1. What Is a Database Transaction?

A transaction is a collection of one or more database operations — SELECT, INSERT, UPDATE, DELETE — executed as a single, logical unit of work.

A transaction has exactly two possible outcomes:

  • Commit — every change made during the transaction is permanently saved.
  • Rollback (abort) — if any operation fails, every change made during the transaction is undone, leaving the database exactly as it was before the transaction started.

📌 Transaction Demarcation

Databases initiate and manage transactions in two primary modes:

  • Explicit transactions — boundaries are manually declared by the engineer using explicit commands (BEGIN TX, COMMIT, ROLLBACK).
  • Implicit transactions (autocommit) — the database engine automatically wraps each standalone query in its own single-statement transaction.

s2. ACID Guarantees Deep Dive

To guarantee data integrity, database management systems enforce four properties, commonly remembered by the acronym ACID. Here is exactly what each letter means, and how the engine implements it.

🛑 A — Atomicity ("All or Nothing")

Atomicity guarantees a transaction is treated as one indivisible unit. Either the entire transaction succeeds, or the entire transaction fails — there is no "half-committed" state.

THE PROBLEM

Transferring $100 from Account A to Account B: the database debits Account A, then the server crashes before it can credit Account B. If left as-is, $100 vanishes into thin air.

THE SOLUTION

Write-ahead logging (WAL) / undo logs. Before modifying data on disk, the database writes the intended change to an append-only log. If a transaction fails mid-way, the engine reads the undo log to reverse the partial changes.

🔄 C — Consistency ("Follow the Rules")

Consistency ensures a transaction can only move the database from one valid state to another — respecting every schema rule, constraint, and invariant along the way.

THE PROBLEM

A table enforces the rule that an account balance can never drop below $0. A transaction tries to withdraw $200 from an account holding only $100.

THE SOLUTION

The database validates schema constraints — NOT NULL, UNIQUE, FOREIGN KEY, CHECK — during execution. Any violation aborts the transaction.

Consistency also relies heavily on Atomicity and Isolation to maintain business-level correctness.

🔒 I — Isolation ("Don't Step on My Toes")

Thousands of transactions run concurrently in production. Isolation ensures their concurrent execution leaves the database in the same state as if they had run one after another — and prevents transactions from seeing each other's uncommitted, in-progress data.

THE PROBLEM

T1 updates a row but hasn't committed. T2 reads that row. T1 then hits an error and rolls back. T2 has now read "dirty" data that technically never existed.

THE SOLUTION

Locking — shared locks for reads, exclusive locks for writes — controls concurrent access. MVCC instead gives each transaction a consistent snapshot, so readers never block writers and writers never block readers.

⚠️ Concurrency Read Phenomena

When isolation controls are relaxed for throughput, three read anomalies become possible:

  • Dirty reads — reading uncommitted data from another in-flight transaction that might still roll back.
  • Non-repeatable reads — reading the same row twice and getting different values, because another transaction committed an update in between.
  • Phantom reads — running the same range query twice and finding new rows, because another transaction committed an insert in between.

💾 D — Durability ("Survive the Apocalypse")

Durability guarantees that once a transaction commits, its changes are permanently recorded on non-volatile storage. Even if the OS crashes or power is lost a millisecond later, the data is not lost.

THE PROBLEM

Writing directly to data files on disk for every change is slow, so databases hold changes temporarily in volatile RAM (the OS page cache). If power cuts out, anything still in RAM vanishes.

THE SOLUTION

fsync(). On commit, the database forces the OS to flush the transaction's log records from RAM to physical disk. The transaction isn't considered committed until the disk controller confirms the WAL bytes are safely written.

s3. Durability & Recovery Techniques

A database's survival through a power failure, OS crash, or server reboot depends entirely on how it implements Durability. Writing every change directly to indexed data pages on disk is expensive — it requires random I/O. Modern engines avoid this with smarter logging and serialization strategies.

💾 Three Core Durability Patterns

1. Write-Ahead Logging (WAL)

Before any in-memory page in the buffer pool is modified, the change is appended sequentially to a transaction log on disk. Sequential writes are dramatically faster than random page updates, letting databases optimize write latency without sacrificing durability.

The Recovery Routine: Redo and Undo

When a database crashes and reboots, it runs a two-step recovery protocol:

  • Redo phase (roll forward) — replay the WAL forward, writing every change from committed transactions that hadn't yet been flushed from the buffer pool to disk.
  • Undo phase (roll back) — use undo logs, or WAL transaction boundaries, to find transactions that were still in-flight at the moment of the crash, and fully reverse their partial writes.

2. Asynchronous Snapshots

Instead of continuous logging, the database takes a full, point-in-time binary dump of its state and saves it to disk asynchronously at set intervals (e.g. every 5 minutes).

THE DURABILITY GAP & COPY-ON-WRITE

Snapshotting a huge database is resource-heavy. On Linux, engines like Redis use fork() to spin off an isolated child process that writes the snapshot dump while relying on copy-on-write — letting the parent process keep serving traffic while the snapshot is taken.

The risk: if the database crashes 4 minutes after the last snapshot, everything written in those 4 minutes is lost. This is the snapshot durability gap.

3. Append-Only File (AOF)

Maintains a continuous ledger of every write command received. Unlike a binary WAL (which logs physical page changes), AOF is a logical, command-based log — e.g. logging the raw command SET user:1 alice.

Fsync Tuning Trade-offs

How durable an AOF is depends entirely on its flush frequency:

  • fsync everysec (default) — flushes to disk once per second. High throughput; at most 1 second of data at risk on crash.
  • fsync always — forces an fsync() for every single write. Maximum durability, at the cost of write throughput.
  • fsync no — lets the OS decide when to flush its buffer cache (typically ~every 30 seconds). Highest performance, lowest durability.

⚡ The Hybrid Solution: Snapshots + AOF

Asynchronous snapshots and AOF each have serious drawbacks in isolation, but their combination is a masterclass in practical durability engineering — Redis uses exactly this as its primary persistence strategy.

  • Bridging the snapshot gap — instead of a multi-minute data-loss window between snapshots, ongoing mutations are continuously appended to the AOF. On crash you lose next to nothing (or at most ~1 second, under everysec).
  • Solving slow AOF recovery — replaying a year of commands from scratch would take hours. In the hybrid layout, the AOF is periodically truncated to hold only the mutations written since the last snapshot.

The RDB–AOF Hybrid Preamble

Modern engines (Redis 4.0+) merge both files during a background rewrite:

  1. A background child process is spawned via fork() to rewrite the append-only file.
  2. The child writes the current database state to the start of the file as a compact binary RDB snapshot (the preamble).
  3. Any writes that happen concurrently are appended to the end of the same file as logical AOF command logs.

On recovery: the engine loads the binary RDB preamble instantly — reconstructing most of the database in milliseconds — then replays the small remaining slice of AOF logs to catch up fully.

📝 Physical Logging vs. Logical Logging

A core design choice in database logging is whether to record physical or logical changes — it directly shapes recovery speed and log size.

Logging typeWhat's recordedProsConsExamples
Physical (WAL) Byte-level changes within physical pages ("set byte 42 to 0x05 on page 4") Fast, deterministic recovery. Safe against partial page writes. Large log sizes. Hard to replicate across engine versions. PostgreSQL WAL, InnoDB redo log
Logical (AOF) The operations executed ("insert Alice into Users", SET user:1 alice) Much smaller logs. Easier to replicate across engine versions. Slow recovery — every write must be re-executed in order. MySQL binary log (statement-based), Redis AOF

Module II — Concurrency & Isolation

s4. Lost Updates (Write-Write Anomalies)

Where read phenomena deal with what a transaction is allowed to see, the lost update is a write-write anomaly: it happens when two transactions run a read-modify-write sequence concurrently against the exact same row.

The Problem, Step by Step

Account A starts with a balance of $100.

  • T1 reads balance ($100). Wants to deposit $50.
  • T2 reads balance ($100). Wants to deposit $20.
  • T1 computes $150 locally, writes balance = 150, commits.
  • T2 computes $120 locally, writes balance = 120, commits.
RESULT

The balance ends at $120. T1's $50 deposit is silently wiped out.

The Engineering Solutions

1. Pessimistic locking (exclusive row locks)

Explicitly lock the row at read time, so no other transaction can touch it until you're done.

SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;

Effect: T2 is blocked from reading the row until T1 commits or aborts.

2. Optimistic concurrency control (OCC) / CAS

Keep a version or updated_at column on the row, and verify it hasn't changed at write time.

UPDATE accounts SET balance = 120, version = 2
WHERE id = 1 AND version = 1;

Effect: if T1 already bumped the version to 2, T2's update matches zero rows — T2 aborts and retries.

3. MVCC snapshot isolation (first-committer-wins)

Under stronger isolation levels (like Repeatable Read in PostgreSQL), the engine actively detects concurrent updates to the same row. On collision, it aborts the second writer outright:

ERROR: could not serialize access due to concurrent update

s5. Transaction Isolation Levels

SQL-92 defines four classical isolation levels, based on which read anomalies each one prevents. Modern engines implement these levels using very different internal architectures — which is exactly why the same isolation level name can behave differently across databases.

📶 The Four Classic Levels, Plus Snapshot Isolation

1. Read Uncommitted (dirty reads allowed)

The lowest tier of isolation — a transaction can see raw, uncommitted writes from other in-flight transactions.

ENGINE REALITY

Most relational databases, including PostgreSQL, don't actually implement Read Uncommitted. Request it, and PostgreSQL silently upgrades your connection to Read Committed.

2. Read Committed (strictly committed reads)

Transactions can only read data that has been permanently committed — this prevents dirty reads.

Each query inside the transaction gets a fresh read snapshot (or acquires and releases locks statement-by-statement). Because snapshots are per-statement, a transaction running multiple queries can see data change between them — allowing non-repeatable reads.

3. Repeatable Read (no value mutation mid-transaction)

Guarantees any row read by a transaction returns the exact same value for the whole duration of that transaction.

4. Snapshot Isolation (point-in-time database snapshots)

An MVCC-specific pattern: when a transaction starts, the database freezes a logical snapshot representing the exact state of the entire database at that instant, and every query in the transaction runs against that static view.

ENGINE DETAIL

PostgreSQL uses Snapshot Isolation to implement its SQL-standard Repeatable Read level — and it's powerful enough to prevent phantom reads too.

5. Serializable (sequential-equivalent execution)

The highest isolation standard: transactions behave as if run in a strict, single-threaded queue. Literal sequential execution would destroy hardware parallelism, so engines optimize it instead:

  • MySQL (InnoDB) — next-key locking: pessimistic range locks on index blocks, stopping concurrent inserts into a queried range.
  • PostgreSQL — Serializable Snapshot Isolation (SSI): transactions run lock-free, but the engine builds an in-memory dependency graph of reads and writes. If it detects a cycle that would break serial order, it aborts the offending transaction.

⚙️ Why Implementations Vary

SQL-92 was written when two-phase locking was the only popular design. The standard defines isolation purely by which anomalies are blocked — so when MVCC engines arrived and bypassed locks entirely, real platform behavior diverged sharply:

s6. MVCC Under the Hood

Modern relational engines avoid reader-writer blocking entirely using Multi-Version Concurrency Control. Under MVCC, updating a row is physically an insert of a new version, paired with a logical deletion of the old one — the database keeps multiple physical copies of the same row alive at once, to serve long-running queries a consistent view.

5 Readers vs. 1 Writer

Row A starts with a balance of $100. Trace how 5 active readers interact with 1 concurrent writer:

  • Readers (Tx 1–5) — active, mid-scan. Because they started before Tx 6 commits, their snapshots freeze Row A at $100.
  • Writer (Tx 6) — runs UPDATE accounts SET balance = 150 WHERE id = A; and commits.
  • The separation — rather than overwriting Row A's bytes, the engine keeps both versions on disk. Tx 1–5 keep reading the old $100 copy; Tx 6 and anything newer reads the committed $150 version. No one blocks, and lock latency is zero.

The MVCC Storage Clutter Penalty (Dead Tuples)

Old row versions aren't deleted in place immediately, which brings real performance costs:

  • Table bloat — dead tuples pile up in physical pages, inflating file size and slowing sequential scans.
  • Write amplification — retaining old versions forces indexes to hold redundant mappings, adding storage overhead.

The Remediation: Vacuum & Purging

  • PostgreSQL VACUUM — background workers scan tables, find rows whose xmax predates the oldest active transaction, and release that slot back to the table heap.
  • MySQL InnoDB purge thread — periodically discards old undo log records and clears overflow pointers, keeping indexes compact.

Heap Multi-Versioning vs. Undo Logging

POSTGRESQL — IN-HEAP

Writes new row copies directly into the main table heap. Active and inactive rows sit side by side. Simple; heavy vacuuming overhead.

INNODB — OUT-OF-HEAP UNDO LOG

Overwrites the row in place, but writes the old bytes to a separate undo tablespace. A reader needing an old version follows a rollback pointer and reconstructs it in RAM on the fly. Main tables stay clean; reconstruction costs CPU.

s7. Non-Repeatable vs. Phantom Reads

A subtle but important line separates these two anomalies. Under the SQL-92 standard they occur at different isolation thresholds, for reasons rooted in the physics of locking.

The Fundamental Difference: Row vs. Range

It comes down to whether the concurrent transaction mutates an existing row, or introduces a brand-new matching row:

  • Non-repeatable reads — Tx A reads a row. Tx B updates or deletes that exact same row and commits. Tx A re-reads it and finds the value changed.
  • Phantom reads — Tx A runs a range query (e.g. WHERE balance > 50) and gets 3 rows. Tx B inserts a new matching row and commits. Tx A re-runs the same query and a 4th, "phantom" row appears.

🔒 Why 2PL Fails at Phantoms

Under traditional two-phase locking, isolation is enforced with physical row locks — which exposes a structural blind spot with inserts.

THE LOCK BLIND SPOT

Tx A runs SELECT * FROM users WHERE age > 30. The engine places a shared lock on every matching row — preventing concurrent UPDATE or DELETE on those rows, which stops non-repeatable reads. But Tx B can still run INSERT INTO users (name, age) VALUES ('Eve', 35), because there was no row for 'Eve' to lock in the first place. It bypasses the locks entirely and appears as a phantom.

The Fix: Next-Key Locking vs. MVCC Snapshots

  • Next-key locking (pessimistic — InnoDB) — locks the gaps between index keys, not just the rows. A range scan for age > 30 blocks any insert into those index slots.
  • MVCC snapshot (optimistic — PostgreSQL) — Tx A runs against a frozen snapshot. Since that snapshot doesn't change when Tx B commits an insert, the new row is naturally filtered out of Tx A's results. Under PostgreSQL, Repeatable Read blocks phantoms with zero row locks.

s9. Consistency: Data (ACID) vs. Reads (CAP)

The word "consistency" is one of the most overloaded terms in database engineering — it describes two entirely different concepts depending on architectural scope.

ACID "C" — CONSISTENCY IN DATA

Application and schema rules, enforced on a single local instance.

CAP "C" — CONSISTENCY IN READS

The speed and uniformity of synchronizing data state across distributed, geographically-spread nodes.

MetricConsistency in data (ACID)Consistency in reads (CAP)
Scope A single database instance Distributed clusters — multiple nodes, globally
Objective Protect data integrity and schema constraints Ensure every reader sees the same value at the same instant
Enforcer Schema engine — validators, constraints, triggers Replication/consensus — Raft, Paxos, quorums
Typical threat Application writes that would break an invariant Network partitions, replication lag
Guarantees NOT NULL, UNIQUE, foreign keys, CHECK Linearizability, read-your-own-writes, eventual consistency

🔒 Consistency in Data — Local Constraints

A data-validity property: moving an instance from one valid, constraint-compliant state to another. If a transaction tries to break a constraint, the engine rejects it and rolls back — the data stays clean because the schema's rules were never allowed to break.

EXAMPLE

Given CHECK (active_users <= maximum_capacity), a single-node PostgreSQL instance that tries to push the count past capacity gets its transaction aborted with a constraint exception.

🌐 Consistency in Reads — Global State

A distributed-state uniformity property, often called linearizability. A production database is rarely one server — primaries and replicas span regions to cut latency and provide failover. A write to a US-East primary takes time to reach a EU-Central replica; the speed of light limits how fast, so a client reading from EU-Central a moment later can see stale data. This is replication lag.

A DISTRIBUTED READ COLLISION

Primary in New York, async replica in London.

1. A user in New York changes their username to "Alice" — the write is accepted by the primary.
2. Before New York replicates to London, a London user queries the London replica for the same username.
3. The London replica returns the old name: "Bob".

Result: a read inconsistency — different clients see different values at the same point in time.

Tuning Read Consistency

  • Synchronous replication — the primary waits for every replica to acknowledge before returning success. Strong consistency, but write latency spikes.
  • Quorum writes (W + R > N) — in systems like Cassandra, the write count (W) plus read count (R) exceeds the total replica count (N), mathematically guaranteeing a read overlaps the latest write.
  • Eventual consistency — accept temporary staleness; replicas catch up once lag drops to zero.
