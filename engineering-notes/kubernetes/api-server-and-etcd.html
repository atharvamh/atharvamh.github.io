Kubernetes Notes

The API Server & etcd

Every piece of Kubernetes is a client of one API, and every fact about the cluster is an object stored behind it. How those objects are shaped, how they are stored and versioned, and how controllers keep a live view of them without hammering the server.

Module I — Everything Is an Object

s1. The Resource Model

Page I ended with controllers that read desired state and observed state and act on the difference. Both kinds of state need a home that every component can read and write. In Kubernetes that home is a single REST API, and everything in the cluster — a Pod, a Node, a Secret, a role binding — is an object exposed through it.

THE PROBLEM

Dozens of components (scheduler, controllers, kubelets, users, CI pipelines, third-party operators) all need to coordinate. Point-to-point APIs between them would mean every component knowing about every other.

THE SOLUTION

One uniform API. Every kind of object supports the same verbs — get, list, watch, create, update, patch, delete — at predictable URLs. Components coordinate only by reading and writing objects.

🧭 Group, Version, Kind — and Resource

  • Group — a family of related APIs (apps, batch, networking.k8s.io). The original types — Pods, Services, ConfigMaps — live in the unnamed core group.
  • Version — the API version (v1, v1beta1). One stored object can be served at several versions; the API server converts between them.
  • Kind — the type name written in your YAML (Deployment). Group + version + kind is the GVK.
  • Resource — the lowercase plural used in the URL (deployments). Group + version + resource is the GVR. Kinds describe data; resources describe endpoints.
kubectl api-resources              # every resource, its group and whether it is namespaced
kubectl get --raw /apis/apps/v1    # the raw discovery document for one group/version
NAMESPACED VS. CLUSTER-SCOPED

Most resources live inside a namespace, a naming scope and policy boundary. A few describe the cluster itself — Nodes, PersistentVolumes, Namespaces themselves, ClusterRoles — and are cluster-scoped. Namespaces scope names and access; they do not isolate the network or the nodes.

s2. Spec vs. Status

Almost every object has the same three-part shape. That shape is the reconciliation loop from Page I, written down as data.

apiVersion: apps/v1
kind: Deployment
metadata:            # identity: name, namespace, uid, labels, ...
  name: web
  generation: 4
spec:                # desired state — written by you
  replicas: 3
status:              # observed state — written by controllers
  observedGeneration: 4
  replicas: 3
  readyReplicas: 2
specstatus
MeaningWhat should be trueWhat was last observed to be true
Written byUsers, CI, higher-level controllersThe controller that owns the object
EndpointThe main resourceThe /status subresource
If lostIntent is goneRebuilt by observing the world again

🔀 Two Writers, Two Endpoints

When a resource has the status subresource enabled, writes to the main endpoint ignore changes to status, and writes to /status ignore changes to everything else. Users and controllers each own their half of the object and cannot clobber the other’s, and RBAC can grant a controller access to deployments/status without letting it change the spec.

🔢 generation & observedGeneration

The API server increments metadata.generation every time the spec changes. When a controller finishes reconciling, it copies the generation it acted on into status.observedGeneration.

READING STATUS CORRECTLY

If observedGeneration < generation, the status describes an older spec — the controller hasn’t caught up with your latest change yet. Tools such as kubectl rollout status check this before trusting any other status field.

s3. Names, Labels & Annotations

metadata carries everything that identifies or describes an object without being part of its desired state.

🪪 Identity

  • name — unique per resource type within a namespace. Chosen by you, or generated from generateName.
  • uid — generated by the API server, unique for the lifetime of the cluster. Delete web and recreate it, and the name matches but the UID does not — which is how other objects can tell a replacement from the original.

🏷️ Labels and Selectors

Labels are short key/value pairs meant to be queried. They are how loosely coupled objects find each other: a Service doesn’t list its Pods by name, it selects every Pod whose labels match.

metadata:
  labels:
    app: web
    tier: frontend

# equality-based and set-based selectors
kubectl get pods -l app=web,tier!=backend
kubectl get pods -l 'env in (staging, prod)'
THE PROBLEM

Pods come and go with new names and IPs. Anything that tracks Pods by name — a Service, a ReplicaSet — would need constant rewiring.

THE SOLUTION

Select by label, not by name. Membership is a query that is re-evaluated continuously, so a new Pod with matching labels joins automatically.

📝 Annotations

Annotations are also key/value pairs, but they are not indexed or selectable. They hold larger, non-identifying data for tools: the last-applied manifest, a build commit, ingress-controller settings. The rule of thumb: if you would ever filter by it, it’s a label; if you only read it once you have the object, it’s an annotation.

s4. Ownership, Deletion & Finalizers

Page I showed a Deployment creating a ReplicaSet, which creates Pods. When you delete the Deployment, something must clean up the rest — without the Deployment controller having to remember everything it ever made.

🔗 ownerReferences

Each dependent object records its owner in metadata.ownerReferences, by kind, name and — crucially — UID.

metadata:
  name: web-7d9f6c-x2k8p
  ownerReferences:
  - apiVersion: apps/v1
    kind: ReplicaSet
    name: web-7d9f6c
    uid: 4b1e…
    controller: true
    blockOwnerDeletion: true

The garbage collector, a controller of its own, deletes any object whose owners no longer exist. Ownership lives on the child, so the graph can be rebuilt at any time just by listing objects.

🧹 Cascading Deletion Policies

PolicyWhat happens
Background (kubectl default)The owner is deleted immediately; the garbage collector deletes dependents afterwards.
ForegroundThe owner stays visible, marked as deleting, until every dependent with blockOwnerDeletion is gone.
OrphanThe owner is deleted; dependents are kept and their owner references removed.
 
kubectl delete deployment web --cascade=foreground
kubectl delete deployment web --cascade=orphan    # keep the ReplicaSet and Pods

⏳ Finalizers: Deletion as a Two-Phase Process

Some objects represent things outside the API — a cloud load balancer, a disk, a backup in object storage. Removing the object from etcd before that external thing is cleaned up would leak it.

THE PROBLEM

A user deletes a PersistentVolumeClaim while a Pod still has it mounted, or deletes an object whose controller still needs to tear down an external resource. If the object vanishes instantly, nobody is left holding the reference.

THE SOLUTION

Finalizers. A delete request only sets metadata.deletionTimestamp. The object stays in place until every entry in metadata.finalizers has been removed by the controller responsible for it.

metadata:
  name: data-claim
  deletionTimestamp: "2026-11-10T09:14:02Z"   # deletion requested
  finalizers:
  - kubernetes.io/pvc-protection              # removed once no Pod uses the claim
THE STUCK-IN-TERMINATING OBJECT

If the controller that owns a finalizer is gone — uninstalled, crashed, misconfigured — the object waits forever. Deleting the finalizer by hand releases the object, but it also skips whatever cleanup the finalizer guarded. Find out what that was first.

Module II — State & Watches

s5. etcd & Raft: Where the Cluster Lives

Every object from Module I is ultimately a key in etcd, a distributed key-value store. etcd is the only stateful component of the control plane: lose it, and the cluster forgets everything it was supposed to be.

/registry/deployments/default/web
/registry/pods/default/web-7d9f6c-x2k8p
/registry/nodes/worker-1
/registry/secrets/kube-system/bootstrap-token-abcdef

Only the API server talks to etcd. Every other component, including the scheduler and the controllers, goes through the API, where requests are authenticated, validated and converted.

THE PROBLEM

Cluster state must survive the loss of a machine, but several copies of it are only useful if every copy agrees on the order of writes. Two replicas that disagree about whether a Pod was bound to node A or node B are worse than one replica.

THE SOLUTION

Raft consensus. One member is elected leader and orders every write into a replicated log. A write is committed only once a majority of members has it on disk, so any surviving majority holds every committed write.

🧮 Quorum Arithmetic

110

532

An even member count adds a machine without adding tolerance, which is why etcd clusters run with 3 or 5 members. More members also mean more acknowledgements per write, so bigger isn’t faster.

🔢 Revisions

etcd keeps a single, cluster-wide revision counter that increases by one with every write. Each key records the revision at which it was last modified (mod_revision). This counter is what makes the next two sections possible: it gives every change a position in one global order.

LIMITS WORTH KNOWING

etcd holds the whole dataset in memory-mapped storage with a default size quota of 2 GB, and rejects any single request over roughly 1.5 MB. That is why a ConfigMap or Secret can’t hold more than about 1 MB, and why etcd is no place for logs or large blobs.

s6. resourceVersion & Optimistic Concurrency

Many writers act on the same objects at once: you scale a Deployment while the Deployment controller is mid-rollout and an autoscaler is adjusting replicas. Kubernetes never locks an object. Instead, every object carries a metadata.resourceVersion, and writes are made conditional on it.

THE PROBLEM

Two clients read the same Deployment, each changes a different field, and each writes the whole object back. The second write silently erases the first client’s change.

THE SOLUTION

Compare-and-swap on resourceVersion. An update must carry the version it read. If the object has changed since, the API server rejects the write with 409 Conflict, and the client re-reads and retries.

📅 A Conflict, Step by Step

TimeClient AClient BStored object
T1Reads web at RV 500Reads web at RV 500RV 500
T2Updates replicas, sends RV 500Accepted → RV 517
T3Updates image, sends RV 500409 Conflict — 500 ≠ 517
T4Re-reads at RV 517, reapplies its change, retriesAccepted → RV 523

Underneath, the API server turns the update into an etcd transaction: if the key’s mod_revision still equals the version the client sent, then write the new value. No locks are held between the read and the write.

// client-go's standard retry helper
err := retry.RetryOnConflict(retry.DefaultRetry, func() error {
    d, err := client.AppsV1().Deployments("default").Get(ctx, "web", metav1.GetOptions{})
    if err != nil {
        return err
    }
    d.Spec.Replicas = ptr.To[int32](5)
    _, err = client.AppsV1().Deployments("default").Update(ctx, d, metav1.UpdateOptions{})
    return err   // a 409 makes RetryOnConflict re-run the whole closure
})
TREAT IT AS OPAQUE

resourceVersion happens to be derived from etcd’s revision today, but the API contract only promises that it changes whenever the object changes. Compare it for equality; never parse it or do arithmetic on it.

Where the Check Does — and Doesn’t — Apply

  • Update (PUT) — always checked: the full object includes its resourceVersion.
  • Patch — not checked unless the patch body includes a resourceVersion. A patch changes only the fields it names, so it rarely needs to be.
  • Server-side apply — conflicts are tracked per field: applying a field another manager owns returns a conflict unless you pass --force-conflicts.

s7. List, Watch & Informers

A controller needs a constantly up-to-date view of the objects it manages. Polling with list every second would bury the API server, so the API offers a second primitive: watch.

# list once, note the collection's resourceVersion...
GET /api/v1/namespaces/default/pods
  → { "metadata": { "resourceVersion": "8812" }, "items": [ ... ] }

# ...then stream every change after it
GET /api/v1/namespaces/default/pods?watch=true&resourceVersion=8812
  → {"type":"ADDED",    "object":{...}}
  → {"type":"MODIFIED", "object":{...}}
  → {"type":"DELETED",  "object":{...}}

List gives the current state at one revision; watch streams every change after that revision. Together they never miss an event and never deliver one twice — the global ordering from s5 at work.

THE PROBLEM

Watches break: connections drop, the API server restarts, and etcd periodically compacts old revisions. Resuming a watch from a revision that has been compacted away is impossible.

THE SOLUTION

The server answers with 410 Gone, and the client falls back to a fresh list followed by a new watch. This is the level-triggered recovery from Page I, built into the protocol. Periodic BOOKMARK events advance the client’s revision so reconnects rarely hit this.

📡 The Informer Pattern

Writing list-and-watch handling, reconnects and caching correctly in every controller would be error-prone, so client-go packages it as an informer.

  • Reflector — runs the list-then-watch loop and handles reconnects and relists.
  • DeltaFIFO — queues each change in order, per object.
  • Indexer — an in-memory, thread-safe cache of every watched object, with optional indexes (for example, Pods by node). Controllers read from here, not from the API server.
  • Event handlers — OnAdd, OnUpdate, OnDelete. In a well-written controller they do nothing but enqueue namespace/name.
  • Workqueue — collapses repeated keys (ten updates to one object become one reconcile), retries failures with backoff, and guarantees a key is never processed by two workers at once.
THE CACHE IS SLIGHTLY STALE

A reconcile reads from the informer cache, which can lag the API server by a few milliseconds — or more under load. A controller may act on state that has already changed. That is safe precisely because of s6: a write based on a stale read fails with a conflict, and the key is requeued.

Shared Informers

Inside one process, a SharedInformerFactory gives every controller that cares about Pods the same informer: one watch connection and one cache, however many consumers. The API server keeps a watch cache of its own, so thousands of watchers don’t each become an etcd watch.

s8. The Request Path

Every write, whether from kubectl, a controller or a kubelet, passes through the same sequence of stages inside the API server before it reaches etcd. Any stage can reject it.

🔐 The Stages

  • Authentication — establishes who is calling: X.509 client certificates, ServiceAccount tokens, OIDC tokens from an identity provider. Kubernetes has no user database of its own; a “user” is just a name an authenticator vouches for.
  • Authorization — decides whether that identity may perform this verb on this resource. Usually RBAC, alongside the Node authorizer that limits each kubelet to its own node’s objects (Page VI).
  • Mutating admission — may modify the object: filling in defaults, injecting a sidecar, attaching a ServiceAccount token. Built-in plugins run first, then mutating webhooks.
  • Schema validation — checks the object against its type’s schema: required fields, value formats, immutable fields.
  • Validating admission — policy checks that can only accept or reject: resource quotas, Pod Security admission, ValidatingAdmissionPolicy rules written in CEL, validating webhooks.
  • Persist — the object is written to etcd with the conditional write from s6, and watchers are notified.
# run the whole pipeline — admission and validation included — without persisting
kubectl apply -f web.yaml --dry-run=server

# ask the authorizer directly
kubectl auth can-i create deployments --namespace default
EXTENSION POINTS

Two of these stages — authentication via webhooks and OIDC, and admission via webhooks and CEL policies — are where most cluster policy and tooling plugs in. Page VII builds an admission webhook.
