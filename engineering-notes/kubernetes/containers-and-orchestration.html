Kubernetes Notes

Containers & the Orchestration Problem

What a container really is once you strip away the tooling, and why running hundreds of them across many machines forces you into declarative state and reconciliation loops — the idea every other part of Kubernetes is built on.

Module I — Containers from Scratch

s1. A Container Is Just a Process

There is no “container” object in the Linux kernel. A container is an ordinary process that the kernel deliberately lies to: it gets its own view of process IDs, network interfaces, mount points and hostname, plus a ceiling on how much CPU and memory it may use. Two kernel features do all the work — namespaces (what a process can see) and cgroups (what a process can use).

THE PROBLEM

Two services on one host both want port 8080, both expect /etc/app/config.yaml to be theirs, and either one can kill the other’s processes. As plain processes, they share a single view of everything.

THE SOLUTION

Namespaces. Each namespace type wraps one global resource so the processes inside get their own isolated copy. A container is simply a process started inside a fresh set of them.

🧱 The Namespace Types

NamespaceIsolatesWhat the process sees
PIDProcess IDsItself as PID 1; no host processes
NetworkInterfaces, IPs, routes, ports, iptables rulesIts own eth0 and its own port 8080
MountMount pointsIts own root filesystem

Try It

sudo unshare --pid --fork --mount-proc --uts bash
hostname container-demo
ps aux        # only bash and ps — and bash is PID 1

From a second terminal, ps aux on the host still lists that same bash with an ordinary PID. One process, two views of the world. That is the whole trick.

⚖️ Containers vs. Virtual Machines

Because there is no guest kernel to boot, a container starts in milliseconds and costs megabytes rather than gigabytes. The price is a weaker isolation boundary: the kernel is shared, so a kernel vulnerability is a vulnerability for every container on the host. Sandboxed runtimes such as gVisor and Kata Containers exist to win back some of that boundary.

WHY THIS MATTERS FOR KUBERNETES

A Pod is a group of containers that deliberately share some namespaces — network, IPC and UTS by default. That is why two containers in the same Pod can reach each other on localhost. We return to this on Page IV.

s2. cgroups: Putting a Ceiling on Resources

Namespaces control what a process can see, not how much it can consume. A process in its own PID and network namespaces can still eat every byte of memory on the host. Control groups (cgroups) organise processes into a hierarchy and attach resource limits and accounting to each group.

THE PROBLEM

The noisy neighbour: one container with a memory leak grows until the host runs out of memory, and the kernel starts killing processes — including ones belonging to other, perfectly healthy containers.

THE SOLUTION

Put each container in its own cgroup with a memory ceiling. When the container exceeds it, the kernel’s OOM killer acts inside that cgroup only, and the neighbours are untouched.

🎛️ cgroup v2 in Practice

Modern distributions use cgroup v2: a single unified hierarchy mounted at /sys/fs/cgroup, where every group is a directory and every limit is a file you write to.

# create a group and set its limits
sudo mkdir /sys/fs/cgroup/demo
echo 100M          | sudo tee /sys/fs/cgroup/demo/memory.max
echo "50000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max   # 50 ms per 100 ms = half a CPU
echo 64            | sudo tee /sys/fs/cgroup/demo/pids.max

# move the current shell (and its future children) into the group
echo $$ | sudo tee /sys/fs/cgroup/demo/cgroup.procs

🔥 Memory Is Incompressible, CPU Is Compressible

The asymmetry in that table is the single most important idea in this section. CPU time can be taken away and handed back later — a throttled process just runs slower. Memory cannot be reclaimed from a process without destroying something, so the only enforcement left is to kill. Kubernetes inherits this exactly: exceed a CPU limit and your latency rises; exceed a memory limit and your container is restarted with the status OOMKilled.

CPU LIMITS BITE IN BURSTS

cpu.max is enforced per period (100 ms by default). A multi-threaded service with a 0.5 CPU limit can spend its entire 50 ms quota early in the period across several threads, then sit fully throttled for the rest of it. Average usage looks low while tail latency spikes. Page IV covers how requests and limits map onto these files.

s3. Images & OverlayFS

Namespaces and cgroups give a process an isolated view and a budget, but it still needs a filesystem to run from: its own /usr/bin, its own libraries, its own application code. An image provides that filesystem.

An image is three things: an ordered list of layers (each a tarball of filesystem changes), a config (entrypoint, environment, working directory, user), and a manifest that ties them together. Every piece is addressed by the SHA-256 digest of its content, so identical layers are stored and downloaded once.

THE PROBLEM

Fifty containers on one host all start from the same 200 MB base image. Copying the full filesystem for each would waste 10 GB of disk and make every start slow.

THE SOLUTION

A union filesystem. Stack the shared, read-only image layers and give each container a thin writable layer on top. Fifty containers share one copy of the base.

📚 How OverlayFS Builds the View

  • lowerdir — the image layers. Read-only and shared by every container started from the image.
  • upperdir — the container’s private writable layer.
  • merged — the union the container sees as /.
  • Read — served from the topmost layer that contains the file.
  • Write to an existing file — copy-up: the whole file is copied from the lower layer into the upper layer, then modified. The image layer is never touched.
  • Delete — a whiteout entry in the upper layer hides the file below it.
# lowerdir is listed top-first: l2 sits above l1
sudo mount -t overlay overlay \
  -o lowerdir=/layers/l2:/layers/l1,upperdir=/c1/upper,workdir=/c1/work \
  /c1/merged

🏷️ Tags vs. Digests

A tag such as nginx:1.27 is a mutable pointer — the registry can repoint it at a different image tomorrow. A digest such as nginx@sha256:… names exact content and can never change. Two nodes pulling the same tag at different times can end up running different code; pin by digest when you need reproducibility.

CONTAINER WRITES ARE EPHEMERAL

The upper layer lives and dies with the container. When Kubernetes restarts a crashed container, it starts a fresh one with an empty writable layer, and anything written there is gone. Copy-up also makes the layer a poor place for large, frequently modified files: changing one byte of a 1 GB file copies the whole gigabyte first. Both problems are what volumes solve (Page VI).

s4. The Runtime Stack: OCI, runc, containerd & CRI

Something has to turn an image into a running process: pull the layers, set up the overlay mount, create the namespaces and cgroups, then execute the entrypoint. That work is split across several components, each with one job, joined together by open specifications.

📜 The OCI Specifications

SpecificationWhat it defines
Image specThe image format: manifest, config and layers
Runtime specA bundle — a root filesystem plus a config.json describing namespaces, cgroups, mounts and the process to run — and its lifecycle: create, start, kill, delete
Distribution specThe HTTP API for pushing images to and pulling them from registries

Because the specifications are open, an image built with Docker, Buildah or kaniko runs on any compliant runtime.

🔧 Who Does What

  • kubelet — the agent on every node. It decides which containers should be running on its node and asks the runtime to make it so.
  • CRI (Container Runtime Interface) — a gRPC API with two services, RuntimeService and ImageService. It exists so the kubelet never depends on any one runtime.
  • containerd / CRI-O — the high-level runtime. It pulls images, unpacks layers into snapshots, prepares the OCI bundle and manages container lifecycle.
  • shim — a small process (for containerd, containerd-shim-runc-v2) that becomes the container’s parent. It holds stdio open and collects the exit code. Because the shim, not containerd, is the parent, containerd can be restarted or upgraded without killing running containers.
  • runc — the low-level runtime. It reads the bundle, makes the namespace, cgroup and mount syscalls, executes the entrypoint, and exits.
WHAT HAPPENED TO DOCKER?

Kubernetes used to talk to Docker through an adapter called dockershim, which was removed in v1.24 (2022). Docker itself runs on containerd and runc, so the change mostly removed a redundant layer. Images built with docker build are OCI images and run unchanged.

Module II — Why Orchestrate

s5. The Many-Machines Problem

Module I gives us a clean way to run an isolated, resource-capped process from a portable image on one machine. Now run 300 of them across 40 machines, for a team that deploys ten times a day. A new class of problems appears, and none of them is about a single container.

ProblemThe manual approachWhat Kubernetes provides
Placement — which machine has room?A spreadsheet of hosts, ssh and docker runThe scheduler (Pages III, IV)
Failure — a machine dies at 3 a.m.A pager, a human, a runbookControllers that recreate Pods elsewhere (Pages III, IV)
Discovery — containers move and IPs changeHard-coded IPs, config pushesServices and DNS (Page V)
Rollout — update 50 replicas without downtimeA scripted loop and hopeDeployments (Page IV)
Scaling — traffic doublesAdd hosts, edit scriptsAutoscalers (Page VII)
Config & secretsFiles copied between hostsConfigMaps and Secrets (Page VI)
THE PROBLEM

Scripts encode steps: “ssh to host 7, start X.” They break the moment reality differs from what the script assumed — a host is down, the container already exists, the previous run failed halfway.

THE SOLUTION

Replace scripts with a system that stores the desired state of the whole cluster and continuously works to make reality match it, however reality drifted.

🏛️ Where the Design Came From

Google open-sourced Kubernetes in 2014, distilled from a decade of running Borg, its internal cluster manager. Two ideas carried over directly: describe what you want rather than how, and let many independent controllers make it so. A third came from Omega, Borg’s research successor: keep all cluster state in one shared store that every component reads from and writes to, using optimistic concurrency rather than locks. In Kubernetes that store is etcd behind the API server — the subject of Page II.

s6. Imperative vs. Declarative

There are two ways to tell a system what to do:

  • Imperative — a sequence of commands: “start three nginx containers.”
  • Declarative — a description of the end state: “there should be three nginx containers.” The system works out the steps.
THE PROBLEM

Run “start 3 containers” twice and you have six. Run it after one crashed and you have five. An imperative command is only correct relative to the state it assumed.

THE SOLUTION

Declare the target, not the steps. “There should be 3” is idempotent: apply it once or ten times, from any starting point, and you end in the same place.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3              # the desired state — not an instruction
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
ImperativeDeclarative
You specifyStepsEnd state
kubectlrun, create, scale, deleteapply -f

Source of truthCommand historyThe manifest, which can live in Git
HOW APPLY KNOWS WHAT TO CHANGE

To work out a diff, apply needs to know which fields you set and which ones the system filled in. Client-side apply stores your last manifest in the kubectl.kubernetes.io/last-applied-configuration annotation. Server-side apply (kubectl apply --server-side) instead records which field manager owns each field in metadata.managedFields, so two tools editing the same object don’t silently overwrite each other.

s7. The Reconciliation Loop

A declaration is just data. Something has to read it and make it true. In Kubernetes that something is a controller, and every controller, however complex, runs the same loop:

for {
    desired := readSpec()      // what the user declared
    actual  := observeWorld()  // what actually exists
    if !equal(desired, actual) {
        act(desired, actual)   // one step toward desired
    }
}

🌡️ It’s a Feedback Controller

This is closed-loop control — the same structure as a thermostat. The setpoint is the spec, the measured value is the observed state, and the controller acts on the error between them. A thermostat doesn’t need to know why the room got cold — an open window, a cold night. A Kubernetes controller doesn’t need to know why a Pod disappeared — a node failure, an eviction, someone running kubectl delete. It sees two Pods where there should be three, and creates one.

🧩 Properties That Fall Out of the Loop

  • Self-healing — any drift, from any cause, is just more error to correct.
  • Idempotent actions — the loop may run many times against the same state, so every action must be safe to repeat.
  • Eventual convergence — reality approaches the spec over successive passes; at any single instant the two may differ.
  • Composition — rather than one giant controller, many small ones each own a single concern.

A Chain of Controllers

kubectl apply on a Deployment starts no containers itself. It writes one object, and a chain of independent controllers each reconciles one step:

  1. The Deployment controller sees the Deployment and creates or updates a ReplicaSet.
  2. The ReplicaSet controller sees that the ReplicaSet wants 3 Pods and creates 3 Pod objects.
  3. The scheduler sees Pods with no node and assigns each one to a node.
  4. The kubelet on that node sees a Pod assigned to it and asks the runtime to start the containers (s4).

None of them calls another. They communicate only by reading and writing objects through the API server.

THE CATCH

Convergence takes time. Right after you apply, spec and status disagree, and anything reading the cluster sees a world in motion. Kubernetes is eventually consistent by design: status always lags spec, and a tool that needs to know when a change has actually landed must wait for it. kubectl rollout status does exactly that, watching the Deployment until every replica is updated and available.

s8. Level-Triggered vs. Edge-Triggered

The terms come from digital electronics. An edge-triggered circuit reacts to a transition — the signal going from 0 to 1. A level-triggered circuit reacts to the current value — the signal being 1. For a controller, the question is whether it acts on events or on state:

  • Edge-triggered: “When a Pod-deleted event arrives, create a Pod.”
  • Level-triggered: “Whenever I run, count the Pods. If there are fewer than desired, create the difference.”
THE PROBLEM

In a distributed system, events get lost: a controller restarts, a network partitions, a watch connection drops. An edge-triggered controller that misses one “Pod deleted” event never replaces that Pod.

THE SOLUTION

Level-triggered logic. Every reconcile reads the full current state and compares it to the spec. A missed event doesn’t matter — the next pass sees the gap and closes it.

📅 A Lost-Event Timeline

T1Spec says 3 replicas; 3 Pods runningIdleIdle

⚙️ What Kubernetes Actually Does

Real controllers use both. A watch delivers events, edge-style, so the controller wakes up immediately instead of polling. But the event is only a hint: “something about object X changed — go look.” The reconcile function then reads the current state of X and acts on that state, level-style.

On startup, a controller first lists every object it cares about — a full read of current state — and only then starts watching. Anything that changed while it was down is caught by that list. Controllers can also set a periodic resync that re-queues every object as a safety net.

THE RULE OF THUMB

Events tell a controller when to look. State tells it what to do. If your reconcile logic ever depends on having seen a particular event, it is edge-triggered, and it will drift.

That is why the API server — and the way clients list and watch it — sits at the centre of everything. That is Page II.
