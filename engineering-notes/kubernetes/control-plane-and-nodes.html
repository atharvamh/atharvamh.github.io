Kubernetes Notes

Control Plane & Node Architecture

The handful of processes that make up a cluster, what each one watches and writes, how they cooperate to turn one kubectl apply into running containers, and what keeps working when any one of them dies.

Module I — The Components

s1. The Shape of a Cluster

A cluster splits into two halves. The control plane stores desired state and decides what should happen. The nodes — the data plane — run the actual workloads. Every component, on either side, is a client of the API server from Page II, and none of them talks to another directly.

ComponentRuns onWatchesWrites
kube-apiserverControl plane—etcd
kube-schedulerControl planePods with no node, NodesPod bindings
kube-controller-managerControl planeAlmost everythingAlmost everything
cloud-controller-managerControl planeNodes, ServicesCloud resources, Node addresses
kubeletEvery nodePods bound to its nodePod status, Node status, its Lease
kube-proxyEvery nodeServices, EndpointSlicesLocal packet-forwarding rules only

s2. kube-apiserver: The Only Door

Page II covered what the API server does — the resource model, conditional writes, watches and the request pipeline. Architecturally, two properties matter:

  • It is stateless. All state lives in etcd, so any number of API server replicas can run side by side behind a load balancer, and any one can serve any request.
  • It is the single choke point. Every read, write and watch from every component goes through it. That is what makes authentication, authorization, admission and auditing enforceable — there is no back door.
THE PROBLEM

A single choke point can be overwhelmed. One misbehaving controller listing every Pod in a loop, or a burst of thousands of new watchers, can starve the kubelets and system controllers that keep the cluster alive.

THE SOLUTION

API Priority and Fairness. Requests are classified into priority levels — system and node traffic above ordinary workload controllers — and queued fairly within each level, so a noisy client exhausts only its own share.

THE WATCH CACHE

Each API server keeps an in-memory cache of recent objects and events per resource type. Most list and watch requests are served from that cache rather than from etcd, so thousands of watchers cost etcd almost nothing.

s3. kube-scheduler: Placing Pods

The scheduler is a controller with one job: find every Pod whose spec.nodeName is empty, choose a node for it, and record the choice. It never starts anything itself.

🎯 Filter, Score, Bind

  1. Filter — discard nodes that cannot run the Pod: not enough unrequested CPU or memory, a taint the Pod doesn’t tolerate, a node selector or affinity rule that doesn’t match, a volume in a different zone.
  2. Score — rank the remaining nodes: spread replicas across zones, prefer nodes that already have the image, balance utilisation.
  3. Bind — write a Binding for the highest-scoring node, which sets the Pod’s spec.nodeName.

Each stage is a set of plugins in the scheduling framework, so the behaviour is configurable without forking the scheduler.

THE SCHEDULER RESERVES NOTHING ON THE NODE

Scheduling is bookkeeping against requests, not actual usage: the scheduler adds up the requests of Pods already bound to each node. Binding a Pod writes one field. The node learns about it only when its kubelet sees the change. Page IV covers requests, limits and the placement rules in depth.

A Pod created with spec.nodeName already set skips the scheduler entirely — the kubelet on that node simply runs it. That is how DaemonSet Pods were placed for years, and why a typo in a hand-set node name leaves a Pod pending forever.

s4. The Controller Managers

Rather than running dozens of separate processes, Kubernetes compiles most of its built-in controllers into a single binary, kube-controller-manager. Each one is an independent reconcile loop with its own informers and workqueue (Page II, s7); they just share a process.

ControllerReconciles
DeploymentDeployments into ReplicaSets, managing rollouts
ReplicaSetThe number of Pods matching a selector
StatefulSet, DaemonSet, Job, CronJobTheir respective workload patterns (Page IV)
Node lifecycleNode health: marks nodes NotReady, taints them, triggers eviction
EndpointSliceWhich ready Pod IPs back each Service (Page V)
NamespaceDeletes everything in a namespace being deleted
ServiceAccount, tokenDefault ServiceAccounts and their credentials
Garbage collectorDependents of deleted owners (Page II, s4)

☁️ cloud-controller-manager

Controllers that need to talk to a cloud provider’s API live in a separate binary maintained by each provider:

  • Node controller — labels nodes with their zone and instance type, sets their addresses, and deletes Node objects whose VM no longer exists.
  • Route controller — programs cloud network routes so Pod traffic can cross nodes, where the network design needs it.
  • Service controller — creates a cloud load balancer for every Service of type LoadBalancer.

Splitting these out lets cloud integrations ship on their own schedule, and lets bare-metal clusters run without any cloud code at all.

s5. kubelet & kube-proxy: The Node Side

🤖 kubelet

The kubelet is the controller for its own node. Its desired state is “the Pods bound to me”; its actual state is whatever the container runtime reports. It reconciles the two continuously:

  • Runs Pods — for each assigned Pod, calls the runtime over CRI (Page I, s4) to create the Pod sandbox, pull images and start containers.
  • Keeps them healthy — runs liveness, readiness and startup probes, and restarts containers according to the Pod’s restart policy.
  • Reports status — writes each Pod’s phase, conditions and container states back through the /status subresource.
  • Reports the node — publishes the node’s capacity and conditions (memory pressure, disk pressure), and renews a Lease object in the kube-node-lease namespace every few seconds as a heartbeat.
  • Protects the node — when memory or disk runs low, evicts Pods before the kernel’s OOM killer has to.
STATIC PODS: HOW THE CONTROL PLANE RUNS ITSELF

The kubelet also runs any Pod manifest it finds in a local directory, usually /etc/kubernetes/manifests, without asking the API server. kubeadm uses this to start etcd, the API server, scheduler and controller manager as Pods on control plane nodes — solving the chicken-and-egg problem of needing an API server to schedule the API server. The kubelet publishes a read-only “mirror Pod” for each one so they still appear in kubectl get pods.

🔀 kube-proxy

kube-proxy watches Services and EndpointSlices and programs the node’s kernel — with iptables, IPVS or nftables rules — so that traffic sent to a Service’s virtual IP lands on one of its backing Pods. Despite the name, in all modern modes it is not in the data path: it writes rules, and the kernel forwards packets. Some network plugins, such as Cilium, replace it entirely with eBPF programs. Page V takes this apart.

s7. Failure Modes: What Breaks When

The most important architectural property of Kubernetes is that the control plane is not in the data path. Containers are run by the node’s runtime and packets are forwarded by its kernel. The control plane only changes what should run. When it fails, the cluster freezes in its current shape rather than collapsing.

Component downRunning workloadsWhat stops working
All API serversKeep running, keep servingEvery change: kubectl, deploys, scaling, self-healing
etcd quorumKeep running, keep servingWrites fail; the cluster is frozen
SchedulerUnaffectedNew Pods stay Pending
controller-managerUnaffectedNo self-healing: lost Pods aren’t replaced, rollouts stall, dead nodes aren’t detected
kubelet on one nodeContainers keep runningNo probes or restarts there; node marked NotReady, then its Pods are evicted
kube-proxy on one nodeExisting rules keep forwardingService changes not applied there; traffic may reach Pods that have gone

💀 When a Whole Node Dies

A dead node can’t report its own death. Detection is the level-triggered pattern again: the absence of a heartbeat is the signal.

  1. The kubelet stops renewing its Lease.
  2. After the node-monitor grace period, the node lifecycle controller marks the node NotReady and adds the taint node.kubernetes.io/unreachable:NoExecute.
  3. Every Pod carries a default toleration for that taint lasting 300 seconds. When it expires, the Pod is evicted — its object is deleted.
  4. The ReplicaSet controller sees fewer Pods than desired and creates replacements; the scheduler places them on healthy nodes.
STATEFULSETS WAIT

A StatefulSet promises that at most one Pod with a given identity exists at a time. Since the control plane can’t tell a dead node from a partitioned one, it won’t start a replacement db-0 while the old one might still be running. The Pod stays stuck until the node is confirmed gone — the Node object is deleted, or the node is marked out of service. Page IV covers why.

Tune the delay per workload with tolerations and tolerationSeconds: shorter for stateless services that should fail over quickly, longer for workloads that are expensive to restart.

s8. High Availability & Leader Election

A production control plane runs on three (or five) machines. How each component is replicated depends on whether it holds state and whether two copies could safely act at once.

ComponentReplication modelWhy
etcdRaft cluster of 3 or 5Holds state; needs a majority to agree (Page II, s5)
kube-apiserverActive–active behind a load balancerStateless; any replica can serve any request
scheduler, controller-managersActive–standby via leader electionTwo active copies would make conflicting decisions — double-scheduling, duplicate Pods
THE PROBLEM

Three controller-manager replicas all watching the same ReplicaSet would each see one missing Pod, and each create a replacement — three Pods instead of one.

THE SOLUTION

Leader election on a Lease object. Replicas race to claim a shared Lease. Only the holder runs its controllers; the others stand by and take over if the leader stops renewing it.

kubectl get lease kube-controller-manager -n kube-system -o yaml
#   spec:
#     holderIdentity: cp-2_6b1f…
#     leaseDurationSeconds: 15
#     renewTime: "2026-11-10T09:20:41.512Z"

⏱️ How the Lease Works

  • The leader renews renewTime every couple of seconds, using a conditional update (Page II, s6), so two candidates can never both win the same round.
  • If the leader can’t renew within its renew deadline, it stops its controllers and exits — it steps down before anyone can take over.
  • Standbys poll the Lease. Once renewTime + leaseDurationSeconds has passed, they try to claim it; exactly one conditional update succeeds.
ONE PRIMITIVE, THREE USES

The same Lease object appears three times on this page: kubelet heartbeats, control plane leader election, and — in your own controllers — controller-runtime’s leader election option. A Lease is just a small object whose meaning comes entirely from a conditional write and a clock.

🏗️ Stacked vs. External etcd

  • Stacked — each control plane node runs an etcd member alongside the API server. Fewer machines and kubeadm’s default, but losing one node loses both an API server and an etcd member.
  • External — etcd runs on its own machines. More hardware, but control plane and storage fail independently, and etcd’s disk latency is isolated from everything else.

Managed services such as EKS, GKE and AKS run all of this for you; the nodes are the only part you see. The architecture underneath is the same.
