Kubernetes Notes

Extending & Operating Kubernetes

How to teach Kubernetes new kinds of objects and new behaviour with the same machinery its built-in controllers use, and how to keep a real cluster healthy: scaling it, seeing inside it, upgrading it and recovering it when things break.

Module I — Extending

s1. Custom Resource Definitions

Everything on Pages II to VI comes down to two ingredients: objects stored behind the API, and controllers reconciling them. Neither is special to the built-in types. A CustomResourceDefinition (CRD) registers a new object type with the API server, and from that moment it gets everything the built-in types get: REST endpoints, storage in etcd, watches, RBAC, admission, kubectl support.

THE PROBLEM

A platform team wants developers to ask for “a website” or “a Postgres cluster” as a single object. Built-in types force them to assemble that out of Deployments, Services, claims and Secrets, and to keep all of them consistent by hand.

THE SOLUTION

Define your own kind. A CRD adds Website to the API, with a schema. A controller (s2) then reconciles each Website into the built-in objects it needs.

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: websites.example.com          # <plural>.<group>
spec:
  group: example.com
  scope: Namespaced
  names: {kind: Website, plural: websites, singular: website, shortNames: [ws]}
  versions:
  - name: v1
    served: true
    storage: true                      # exactly one version is the storage version
    subresources:
      status: {}                       # spec/status split, as in Page II, s2
    additionalPrinterColumns:
    - {name: Ready, type: string, jsonPath: .status.ready}
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            required: [image]
            properties:
              image:    {type: string}
              replicas: {type: integer, minimum: 1, maximum: 20}
            x-kubernetes-validations:  # CEL, evaluated by the API server
            - rule: "self.image.contains(':')"
              message: "image must include a tag"
          status:
            type: object
            properties:
              ready: {type: string}
kubectl apply -f website-crd.yaml
kubectl get --raw /apis/example.com/v1      # the new group and version, served like any other
kubectl get websites                        # works, with the printer column
A CRD ALONE DOES NOTHING

Creating a Website now stores it and validates it — and that is all. Like a Deployment with no Deployment controller, it is desired state that nobody acts on. The behaviour comes from a controller.

THE OTHER EXTENSION MECHANISM

For APIs that can’t be backed by etcd — live metrics, for example — Kubernetes can instead proxy a whole API group to a separate server, registered with an APIService object. This is the aggregation layer. metrics-server uses it to serve metrics.k8s.io, which is what kubectl top reads. CRDs cover nearly every other case.

s2. Writing a Controller

Page II, s7 described the machinery a controller needs: informers, a cache, a workqueue, retries. Writing that by hand with client-go is possible but repetitive. Most controllers are built with controller-runtime, usually scaffolded by Kubebuilder or the Operator SDK. You supply one function.

func (r *WebsiteReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var site webv1.Website
    if err := r.Get(ctx, req.NamespacedName, &site); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err) // deleted: owned objects are GC'd
    }

    // Desired child, computed purely from the spec. No "what changed?" logic.
    dep := &appsv1.Deployment{ObjectMeta: metav1.ObjectMeta{Name: site.Name, Namespace: site.Namespace}}
    _, err := controllerutil.CreateOrUpdate(ctx, r.Client, dep, func() error {
        dep.Spec = desiredDeploymentSpec(&site)
        return controllerutil.SetControllerReference(&site, dep, r.Scheme) // ownerReference
    })
    if err != nil {
        return ctrl.Result{}, err // requeued with backoff
    }

    site.Status.Ready = readiness(dep)
    if err := r.Status().Update(ctx, &site); err != nil { // the /status subresource
        return ctrl.Result{}, err // a 409 conflict lands here too, and retries
    }
    return ctrl.Result{}, nil
}

func (r *WebsiteReconciler) SetupWithManager(mgr ctrl.Manager) error {
    return ctrl.NewControllerManagedBy(mgr).
        For(&webv1.Website{}).        // reconcile when a Website changes
        Owns(&appsv1.Deployment{}).   // ...or when a Deployment it owns changes
        Owns(&corev1.Service{}).
        Complete(r)
}

✅ The Rules, Restated as Code

  • Level-triggered (Page I, s8) — the request carries only a name. Reconcile reads current state and computes the desired children from the spec, every time.
  • Idempotent — CreateOrUpdate is safe to run a hundred times against the same state.
  • Owner references (Page II, s4) — deleting the Website garbage-collects its children with no cleanup code, and Owns uses them to map a child’s change back to its parent.
  • Errors mean retry — return an error and the workqueue retries with backoff. Return RequeueAfter to check again later even without an error.
  • Status through the subresource (Page II, s2) — never mix spec and status writes.
EXTERNAL RESOURCES NEED FINALIZERS

Owner references only clean up objects inside the cluster. If reconcile creates something outside — a DNS record, a cloud bucket — add a finalizer (Page II, s4) when you create it, delete the external thing when deletionTimestamp is set, then remove the finalizer. Otherwise every deleted Website leaks one.

s3. The Operator Pattern

An operator is a CRD plus a controller that encodes what a human operator knows about running one specific piece of software. The built-in StatefulSet gives a database stable identity (Page IV, s4), but knows nothing about databases. An operator does.

THE PROBLEM

Running a replicated database means procedures: initialise a primary, join replicas, fail over when the primary dies, take consistent backups, upgrade one member at a time. Written as a runbook, every step waits for a human.

THE SOLUTION

Turn the runbook into a reconcile loop. The user declares kind: PostgresCluster with instances: 3; the operator watches the real cluster and performs each procedure whenever observed state drifts from that declaration.

Capability levelThe operator can
1. Basic installDeploy the software from a custom resource
2. Seamless upgradesUpgrade the software and itself safely
3. Full lifecycleBack up, restore, fail over, scale
4. Deep insightsExpose metrics, alerts and health in application terms
5. Auto pilotTune and heal itself: autoscale, detect anomalies, fix them

These are the Operator Framework’s capability levels. Most real value lives at level 3: the procedures that are rare, risky and easy to get wrong by hand.

WHEN NOT TO WRITE ONE

An operator is software you must maintain, upgrade and secure, usually with broad permissions. If the need is “install these manifests with some parameters”, a templating tool such as Helm or Kustomize is enough. Reach for an operator when there is ongoing operational logic — something has to keep watching and acting.

s4. Admission Webhooks

Page II, s8 showed two admission stages in the request path, and Page VI, s9 used CEL policies inside the validating one. When a rule needs real code — an external lookup, a complex mutation — the API server can call out to your own HTTPS service.

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata: {name: require-team-label}
webhooks:
- name: require-team-label.example.com
  admissionReviewVersions: [v1]
  sideEffects: None
  failurePolicy: Fail            # if the webhook is unreachable: reject (or Ignore: allow)
  timeoutSeconds: 5
  rules:
  - {apiGroups: [apps], apiVersions: [v1], operations: [CREATE, UPDATE], resources: [deployments]}
  namespaceSelector:             # never apply to the namespaces that run the cluster itself
    matchExpressions:
    - {key: kubernetes.io/metadata.name, operator: NotIn, values: [kube-system, webhooks]}
  clientConfig:
    service: {name: policy-webhook, namespace: webhooks, path: /validate}
    caBundle: LS0tLS1CRUdJTi…     # to verify the webhook's serving certificate
func validate(w http.ResponseWriter, r *http.Request) {
    var review admissionv1.AdmissionReview
    json.NewDecoder(r.Body).Decode(&review)

    var dep appsv1.Deployment
    json.Unmarshal(review.Request.Object.Raw, &dep)

    resp := &admissionv1.AdmissionResponse{UID: review.Request.UID, Allowed: true}
    if dep.Labels["team"] == "" {
        resp.Allowed = false
        resp.Result = &metav1.Status{Message: "every Deployment needs a team label"}
    }
    review.Response = resp
    json.NewEncoder(w).Encode(review)
}
THE PROBLEM

With failurePolicy: Fail, a crashed webhook blocks every matching write in the cluster. If its rules also match its own Pods — or the system Pods that would restart it — nothing can recover: the fix is itself rejected.

THE SOLUTION

Exclude the webhook’s own namespace and system namespaces with a namespaceSelector, run several replicas with a PodDisruptionBudget, keep timeoutSeconds short, and prefer a CEL ValidatingAdmissionPolicy whenever the rule can be written in CEL — it runs inside the API server and can’t go down separately.

SIDE EFFECTS AND RE-ORDERING

A webhook may be called for requests that are later rejected by another stage, or for dry runs, so it must not change anything outside the response — hence sideEffects: None. Mutating webhooks can also run in any order and may be re-invoked after another webhook changes the object, so each mutation must be idempotent.

Module II — Operating

s5. Autoscaling

Load changes over the day; a fixed replica count is either wasteful or too small. Kubernetes splits autoscaling into three independent controllers, each reconciling a different number.

↔️ Horizontal Pod Autoscaler

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: web}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: web}
  minReplicas: 3
  maxReplicas: 30
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: {type: Utilization, averageUtilization: 70}   # 70% of the CPU *request*

Every 15 seconds or so it applies one formula, then writes the result to the Deployment’s replica count:

desired = ceil( current × currentMetric / targetMetric )
        = ceil( 4 × 91% / 70% ) = ceil(5.2) = 6

Utilization is measured against the Pod’s request (Page IV, s6), so an HPA on CPU is meaningless without CPU requests. Scale-down waits through a stabilization window (five minutes by default) so a brief dip doesn’t remove replicas that will be needed again a minute later. Beyond CPU and memory, the HPA can follow custom metrics such as queue length or requests per second.

↕️ Vertical Pod Autoscaler

The VPA watches actual usage over time and recommends — or applies — better requests. In Off mode it only publishes recommendations; in Initial it sets requests when Pods are created; in Auto it may evict Pods to restart them at the new size. Never let the HPA and VPA both act on the same CPU or memory metric: the VPA raising requests lowers utilization, and the HPA scales in response to a change it didn’t cause.

🏗️ Cluster Autoscaler

  • Scale up — when Pods are Pending because no node has room, it simulates which node group would fit them and grows that group.
  • Scale down — when a node’s requested resources stay low for a while and its Pods could fit elsewhere, it drains the node through the Eviction API, respecting PodDisruptionBudgets (Page IV, s8), then removes it.

It reasons entirely in requests, not usage — another reason honest requests matter. Karpenter takes a different approach: instead of resizing predefined node groups, it chooses and launches a right-sized instance for the pending Pods directly.

s6. Observability

A cluster produces four different kinds of signal, each with its own source, lifetime and tool. Most debugging confusion comes from looking in the wrong one.

SignalSourceKept forAnswers
EventsControllers, scheduler, kubeletAbout an hour by defaultWhat did Kubernetes just do, and why did it fail?
LogsContainer stdout and stderrUntil rotated or the Pod is goneWhat did the application say?
Metricskubelet, kube-state-metrics, appsAs long as your metrics store keeps themHow much, how fast, over time?
Audit logAPI serverAs configuredWho changed what, when?

📜 Logs

Containers should log to stdout and stderr. The runtime writes those streams to files under /var/log/pods/ on the node, the kubelet rotates them, and kubectl logs reads them through the kubelet. Once a Pod is deleted or rescheduled, its logs go with it — so production clusters run a log collector as a DaemonSet (Page IV, s5) that tails those files and ships them to central storage.

📈 Metrics

  • metrics-server — a short window of current CPU and memory per Pod and node, served through the aggregation layer (s1). It feeds kubectl top and the HPA, and is not a monitoring system.
  • kubelet / cAdvisor — detailed per-container resource metrics, read straight from the cgroups of Page I, s2.
  • kube-state-metrics — turns object state into metrics: desired vs. available replicas, Pod phases, restart counts. It answers “is the cluster converged?”
  • Prometheus (or a compatible system) scrapes all of these, plus your applications, and keeps history for dashboards and alerts.

🔬 Debugging Inside a Pod

Minimal images ship without a shell or tools, and a crashed container can’t be exec’d into. An ephemeral container joins a running Pod’s namespaces with an image of your choice:

kubectl debug -it web-7d9f6c-x2k8p --image=busybox --target=web   # share web's process namespace
kubectl debug node/worker-1 -it --image=ubuntu                     # a Pod on the node, host filesystem at /host

s7. Upgrades & Version Skew

Kubernetes releases a new minor version roughly three times a year, and each is supported for about a year. Clusters must be upgraded continuously, and without downtime.

📏 The Version Skew Policy

Components are never all upgraded at the same instant, so Kubernetes defines which mixes of versions are supported. The rule of thumb: nothing may be newer than the API server.

ComponentAllowed relative to kube-apiserver
Other API server replicasWithin one minor version of each other
controller-manager, schedulerSame, or one minor version older
kubelet, kube-proxySame, or up to three minor versions older; never newer
kubectlOne minor version older or newer

🪜 The Order of Operations

  1. Back up etcd (s8). It is the only state; everything else can be rebuilt.
  2. Check for removed APIs. Find manifests, Helm charts and controllers still using API versions the target release removes, and migrate them first.
  3. Upgrade the control plane, one minor version at a time, one node at a time: API servers first, then controller-manager and scheduler.
  4. Upgrade nodes one at a time, or in small batches: cordon, drain (respecting PDBs), upgrade the kubelet, uncordon. Or replace nodes with fresh ones on the new version.
kubectl cordon worker-1                                      # no new Pods here
kubectl drain worker-1 --ignore-daemonsets --delete-emptydir-data
#   ...upgrade kubelet and runtime, restart...
kubectl uncordon worker-1
THE PROBLEM

A Deployment manifest uses an API version that was deprecated releases ago and is removed in the target version. After the upgrade, every CI pipeline that applies it starts failing — and objects stored under the old version must already have been migrated.

THE SOLUTION

Read the deprecation guide for every release you cross, and watch the API server’s apiserver_requested_deprecated_apis metric, which records which deprecated APIs clients are still calling — and update those clients before the version that removes them.

WHY DRAINING IS SAFE

Draining is the Eviction API (Page IV, s8) applied to every Pod on a node. PDBs throttle it, controllers recreate the Pods elsewhere (Page I, s7), and graceful termination (Page IV, s2) lets each one finish in-flight work. An upgrade is just the reconciliation machinery working as designed.

s8. Failure Modes in Practice

Page III, s7 showed what happens when one component dies. In real clusters, outages more often come from slow-burning problems that touch everything at once.

💾 Backing Up etcd

# take a consistent snapshot from a healthy member
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-$(date +%F).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# restore into a new data directory, then point etcd at it
etcdutl snapshot restore /backup/etcd-2026-11-10.db --data-dir /var/lib/etcd-restored
WHAT AN ETCD RESTORE REALLY DOES

Restoring rewinds the whole cluster’s desired state to the snapshot — but not the world. Pods that ran since, disks provisioned since, load balancers created since all still exist outside etcd. Controllers then reconcile reality toward the old state, which can delete things. Restoring etcd is for losing the control plane, not for undoing a bad deploy. Volume data isn’t in etcd at all; that is what snapshots and backups are for (Page VI, s5). Remember too that an etcd backup contains every Secret — encrypted only if encryption at rest was on (Page VI, s6).

THE CERTIFICATE TIME BOMB

kubeadm issues control plane certificates valid for one year. A cluster that has never been upgraded stops working on the anniversary of its creation. Upgrading with kubeadm renews them, which is one more reason to upgrade regularly.

🧭 The Whole Series in Seven Lines

  1. A container is a process with namespaces, cgroups and a layered filesystem; orchestration is a reconciliation loop over declared state.
  2. All state is objects in one API backed by etcd, versioned for conditional writes and streamed through watches.
  3. Components never call each other; each watches objects and writes its own small part.
  4. Pods are the unit; controllers give them replication, identity, per-node placement or completion; requests decide placement and limits become cgroups.
  5. Every Pod has a routable IP; Services are virtual IPs implemented as kernel rules; DNS, gateways and policies build on them.
  6. Storage, configuration and identity are objects too, plugged into real systems through CSI and guarded by RBAC and admission.
  7. Extending Kubernetes is the same pattern again: your own objects, your own controllers.
