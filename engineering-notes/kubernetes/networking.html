Kubernetes Notes

Networking

How every Pod gets a real IP address that any other Pod can reach, how packets actually move inside and between nodes, and how Services, DNS, gateways and policies turn a flat network of short-lived Pods into stable, discoverable, controlled endpoints.

Module I — The Pod Network

s1. The Kubernetes Network Model

Before Kubernetes, the usual way to network containers was port mapping: containers got private addresses behind the host, and the outside world reached them through host ports — host port 32768 forwarded to container port 80. Kubernetes rejects that model outright.

THE PROBLEM

With port mapping, every application must learn which host port it was given, two Pods can’t both use port 80 on one node, and an address a container sees for itself differs from the address others use to reach it. Every service-discovery and configuration system has to work around NAT.

THE SOLUTION

An IP per Pod on a flat network. Every Pod gets its own routable address, and every Pod can reach every other Pod at that address, on any node, with no NAT in between. A Pod behaves like a small VM on a LAN.

📜 The Three Rules

  1. Every Pod can communicate with every other Pod on any node without NAT.
  2. Agents on a node (the kubelet, system daemons) can communicate with every Pod on that node.
  3. The IP a Pod sees for itself is the same IP others use to reach it.

Kubernetes states these rules but does not implement them. The kubelet and API server know nothing about routes or bridges. Implementing the model is delegated to a network plugin through the CNI interface (s4) — which is why clusters can network in very different ways and still behave identically to applications.

s2. Inside a Node: veth Pairs & the Bridge

Each Pod has its own network namespace (Page I, s1), with its own interfaces and routing table. A namespace starts out completely disconnected. Two kernel primitives wire it to the host:

  • veth pair — a virtual Ethernet cable with two ends. A packet sent into one end comes out of the other. One end goes inside the Pod’s namespace and is renamed eth0; the other stays in the host namespace.
  • Bridge — a virtual switch in the host namespace. The host ends of every Pod’s veth pair plug into it, so Pods on the same node can reach each other at layer 2.
# build one by hand: a namespace, a veth pair, a bridge
sudo ip netns add podA
sudo ip link add veth-a type veth peer name eth0 netns podA
sudo ip link add cni0 type bridge
sudo ip link set veth-a master cni0
sudo ip addr add 10.244.1.1/24 dev cni0
sudo ip netns exec podA ip addr add 10.244.1.2/24 dev eth0
sudo ip netns exec podA ip route add default via 10.244.1.1
# (plus: ip link set ... up on each interface)
NOT EVERY PLUGIN USES A BRIDGE

The bridge is the classic design. Calico, for example, skips it: each veth host end gets a /32 route, and the node routes between Pods at layer 3. Cilium attaches eBPF programs to the veth interfaces and forwards packets before they reach most of the kernel’s networking stack. The model from s1 holds either way.

s3. Across Nodes: Routing vs. Overlays

Each node is typically given its own slice of the cluster’s Pod address range — its Pod CIDR, recorded in node.spec.podCIDR (for example 10.244.1.0/24 for node 1, 10.244.2.0/24 for node 2). Within a node, s2 solved delivery. Between nodes, the physical network has never heard of 10.244.2.0/24. There are two ways to fix that.

THE PROBLEM

Pod A on node 1 (10.244.1.2) sends to Pod C on node 2 (10.244.2.5). Node 1 forwards it toward the network — but the switches and routers between the nodes have no route for Pod addresses and drop the packet.

THE SOLUTION

Either teach the network the Pod routes (routed mode), or hide Pod packets inside node-to-node packets the network already understands (overlay mode).

🛣️ Routed Mode

Every node’s Pod CIDR is announced as a route pointing at that node’s IP: through BGP (Calico’s classic mode), through cloud route tables (the route controller from Page III, s4), or through static routes when all nodes share a layer-2 segment. Packets travel unmodified — fast and easy to debug — but the underlying network must cooperate.

🧅 Overlay Mode

The sending node wraps the Pod-to-Pod packet inside a new packet addressed node-to-node, usually with VXLAN (an Ethernet frame carried in UDP). The network sees only ordinary traffic between node IPs. The receiving node unwraps it and delivers the inner packet.

RoutedOverlay

MTU: THE CLASSIC OVERLAY BUG

VXLAN adds about 50 bytes per packet. If the Pod interface keeps the underlay’s 1500-byte MTU, full-size packets no longer fit once wrapped. Small requests work; large responses mysteriously hang. Overlay plugins set the Pod MTU lower (typically 1450) for exactly this reason.

A third approach sidesteps the question: cloud-native plugins such as the AWS VPC CNI give Pods real addresses from the cloud network itself, so the network already knows every Pod IP — at the cost of consuming the VPC’s address space.

s4. CNI: The Plugin Contract

The Container Network Interface is a deliberately small specification. A CNI plugin is just an executable. The container runtime runs it when it creates or destroys a Pod sandbox (Page I, s4) and tells it what to do through environment variables and a JSON config on stdin.

CommandThe plugin must
ADDAttach the given network namespace to the network: create interfaces, assign an IP, set routes. Return the result as JSON.
DELUndo everything ADD did and release the IP. Must succeed even if called twice.
CHECKVerify the attachment is still as expected
VERSIONReport which spec versions the plugin supports
 
# what the runtime effectively does on Pod creation
CNI_COMMAND=ADD \
CNI_CONTAINERID=3f9c… \
CNI_NETNS=/var/run/netns/cni-1a2b… \
CNI_IFNAME=eth0 \
CNI_PATH=/opt/cni/bin \
/opt/cni/bin/bridge < /etc/cni/net.d/10-mynet.conflist

# stdout
{ "ips": [ { "address": "10.244.1.2/24", "gateway": "10.244.1.1" } ], ... }

🧱 Plugins Compose

  • Main plugins create the interface: bridge, ptp, macvlan.
  • IPAM plugins hand out addresses: host-local allocates from the node’s Pod CIDR and records leases on local disk.
  • Chained plugins run after the main one to add features — port mappings, bandwidth limits.

Full network solutions — Flannel, Calico, Cilium — ship a CNI binary for the per-Pod plumbing plus a DaemonSet agent (Page IV, s5) on every node that handles the cluster-wide part: distributing routes, programming tunnels, enforcing NetworkPolicy (s9).

WHY NEW NODES ARE NOTREADY

A freshly joined node reports NotReady with a message that the network plugin isn’t initialised until a CNI config file appears in /etc/cni/net.d. Without one, the runtime can’t create any Pod sandbox, so the node is unusable — which is why installing a network plugin is the first step after kubeadm init.

Module II — The Service Layer

s5. Services: Stable Virtual IPs

Module I made every Pod reachable. But Pod IPs are useless as addresses for clients: Pods are replaced on every rollout, rescheduled after every node failure, and scaled up and down. A client holding a Pod IP is holding something that will stop working.

THE PROBLEM

Clients need one stable address for “the web backend”, while the set of Pods behind it changes constantly — and traffic should spread across all of them and skip the ones that aren’t ready.

THE SOLUTION

A Service. A stable virtual IP and DNS name, plus a label selector. Traffic to the virtual IP is spread across whichever ready Pods currently match the selector.

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector: {app: web}        # membership by label (Page II, s3)
  ports:
  - port: 80                  # the Service's port
    targetPort: 8080          # the containers' port

📇 EndpointSlices

The Service object doesn’t list its Pods. A controller (Page III, s4) watches Services and Pods and writes EndpointSlices: lists of Pod IPs, ports and readiness for each Service, at most 100 endpoints per slice by default. Splitting into slices means a change to one Pod in a 5,000-Pod Service rewrites one small object, not a giant one that every node must download again.

The first three are nested: a LoadBalancer Service is also a NodePort Service, which is also a ClusterIP Service.

s6. How kube-proxy Implements Services

A ClusterIP is not assigned to any interface on any machine. No process listens on it. It exists only as a rule in each node’s kernel that says “packets to this address should go somewhere else”. kube-proxy (Page III, s5) watches Services and EndpointSlices and keeps those rules in sync.

⛓️ iptables Mode, Step by Step

  1. A packet from a Pod to 10.96.12.7:80 enters the nat table, which jumps to KUBE-SERVICES.
  2. A rule matching that destination jumps to the Service’s chain, KUBE-SVC-….
  3. That chain picks one endpoint chain using the kernel’s random statistic match.
  4. The endpoint chain DNATs the packet: rewrites its destination to the chosen Pod’s IP and port.
  5. The packet is now an ordinary Pod-to-Pod packet and travels as in Module I. conntrack records the translation, so replies are rewritten back to appear to come from the Service IP.
sudo iptables -t nat -L KUBE-SERVICES -n | grep 10.96.12.7
sudo iptables -t nat -L KUBE-SVC-4N57… -n
sudo conntrack -L -d 10.96.12.7
LOAD BALANCING IS PER CONNECTION

The random choice happens once per connection, not per request. A client that opens one long-lived connection — gRPC over HTTP/2, a database pool — sends all its traffic to one Pod, and new Pods added by scaling get nothing until clients reconnect. Balancing individual requests needs a layer-7 proxy or client-side balancing.

🌍 Traffic from Outside: Source IPs

A NodePort or LoadBalancer packet can arrive at a node with no local Pod for the Service. By default (externalTrafficPolicy: Cluster), that node forwards it to a Pod elsewhere and must SNAT it so the reply comes back the same way — and the Pod sees the node’s IP instead of the client’s. Setting externalTrafficPolicy: Local delivers only to Pods on the receiving node, preserving the client IP. Nodes without a local Pod then fail the load balancer’s health check, so it stops sending them traffic.

s7. DNS & Service Discovery

Virtual IPs are stable, but nobody wants to hard-code 10.96.12.7. Clusters run a DNS server — almost always CoreDNS, as a Deployment behind a Service conventionally named kube-dns — that watches Services and EndpointSlices and answers queries from them.

📖 The Records

NameResolves to

db-0.db.default.svc.cluster.localOne StatefulSet Pod’s IP (Page IV, s4)

🔎 How a Short Name Resolves

The kubelet writes every Pod’s /etc/resolv.conf:

nameserver 10.96.0.10                 # the kube-dns Service
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

A name with fewer than five dots is tried with each search suffix first. From a Pod in default, web becomes web.default.svc.cluster.local and resolves on the first try. web.payments becomes web.payments.svc.cluster.local after one miss — which is how you reach a Service in another namespace.

THE PROBLEM

api.github.com has only two dots, so it is first tried as api.github.com.default.svc.cluster.local, then the other suffixes — several failed queries, for both IPv4 and IPv6, before the real lookup. At high request rates this multiplies DNS load and adds latency.

THE SOLUTION

Use a fully qualified name with a trailing dot (api.github.com.), lower ndots for that Pod through dnsConfig, or run NodeLocal DNSCache so repeated lookups are answered on the node.

s8. Ingress & Gateway API

Services work at layer 4: IPs and ports. Exposing HTTP applications needs layer-7 decisions — route /api to one Service and / to another, terminate TLS, pick a backend by host name — and one shared entry point rather than a cloud load balancer per Service.

🚪 Ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
spec:
  ingressClassName: nginx
  tls:
  - hosts: [shop.example.com]
    secretName: shop-tls
  rules:
  - host: shop.example.com
    http:
      paths:
      - {path: /api, pathType: Prefix, backend: {service: {name: api, port: {number: 80}}}}
      - {path: /,    pathType: Prefix, backend: {service: {name: web, port: {number: 80}}}}

An Ingress object is only configuration. Nothing happens until an Ingress controller — a reverse proxy such as NGINX, HAProxy, Traefik or Envoy, packaged with a controller that watches Ingress objects — is installed and translates them into proxy config. The controller itself is exposed through a LoadBalancer Service.

THE PROBLEM

The Ingress API covers only basic host and path routing. Everything else — header matching, traffic splitting, timeouts, rewrites — was bolted on through controller-specific annotations, so the same Ingress means different things on different controllers. One object also mixes concerns that belong to different people: the shared load balancer and an individual team’s routes.

THE SOLUTION

Gateway API. A richer, portable set of resources, split by role. Ingress remains supported but is feature-frozen; new capabilities go into Gateway API.

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: checkout
  namespace: shop
spec:
  parentRefs: [{name: public, namespace: infra}]    # attach to a shared Gateway
  hostnames: [shop.example.com]
  rules:
  - matches: [{path: {type: PathPrefix, value: /checkout}}]
    backendRefs:                                      # a canary, natively
    - {name: checkout-v1, port: 80, weight: 90}
    - {name: checkout-v2, port: 80, weight: 10}

s9. NetworkPolicy

The flat network from s1 has a security consequence: by default every Pod can reach every other Pod, in every namespace. A compromised frontend can talk directly to the database.

THE PROBLEM

Pod IPs change constantly, so firewall rules written in terms of IP addresses go stale within minutes.

THE SOLUTION

NetworkPolicy. Firewall rules written in terms of labels and namespaces. The network plugin translates them into IP-level rules and keeps them current as Pods come and go.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-allow-api
  namespace: shop
spec:
  podSelector:
    matchLabels: {app: db}           # the Pods this policy protects
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels: {app: api}      # only api Pods in this namespace...
    ports:
    - {protocol: TCP, port: 5432}    # ...and only on the database port

🧠 The Semantics

  • Default allow. A Pod that no policy selects accepts all traffic.
  • Selection isolates. As soon as any policy selects a Pod for a direction (ingress or egress), that direction becomes deny-by-default for that Pod.
  • Rules only allow. There are no deny rules. The permitted traffic is the union of every policy that selects the Pod, so policies are additive and their order doesn’t matter.
  • Replies are implicit. Policies are stateful: allowing a connection allows its return traffic.
# the usual starting point: deny all ingress in a namespace, then allow selectively
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: shop
spec:
  podSelector: {}          # every Pod in the namespace
  policyTypes: [Ingress]   # with no ingress rules: nothing is allowed in
POLICIES ARE ONLY AS GOOD AS THE PLUGIN

The API server accepts NetworkPolicy objects whether or not anything enforces them. With a plugin that doesn’t implement policy — basic Flannel, for instance — the policies are silently ignored. And when you add egress isolation, remember to allow DNS (port 53 to kube-dns), or every name lookup in the namespace starts failing.

WHERE THIS CONTINUES

NetworkPolicy controls which Pods can talk; it doesn’t prove who is talking or encrypt anything. Workload identity and API access control are covered on Page VI.
