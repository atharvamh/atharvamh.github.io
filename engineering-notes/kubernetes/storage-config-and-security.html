Kubernetes Notes

Storage, Config & Security

How data outlives the containers that write it, how storage systems plug in through one contract, and how configuration, secrets, workload identity, RBAC and admission policy decide what each Pod can read, reach and do.

Module I — Storage

s1. Volumes: Beyond the Container Layer

Page I ended with a warning: a container’s writable layer dies with the container. Restart it and every file it wrote is gone, and two containers in the same Pod can’t see each other’s files at all.

THE PROBLEM

Containers need data that survives a restart, data shared with a sidecar, files of configuration injected from outside, and — for databases — data that survives the Pod itself being deleted and rescheduled.

THE SOLUTION

Volumes. A directory declared at the Pod level and mounted into any of its containers. What backs the directory, and how long it lives, depends on the volume type.

spec:
  volumes:
  - name: scratch
    emptyDir: {}                 # declared once, at the Pod level
  containers:
  - name: app
    volumeMounts:
    - {name: scratch, mountPath: /tmp/work}
  - name: sidecar
    volumeMounts:
    - {name: scratch, mountPath: /data, readOnly: true}

📦 Volume Types by Lifetime

TypeBacked byLives as long as
emptyDirNode disk, or RAM with medium: MemoryThe Pod — survives container restarts, deleted with the Pod
configMap, secret, projectedAPI objects written to files by the kubeletThe source object (s6)
hostPathA directory on the nodeThe node
persistentVolumeClaimNetwork or local storage managed by KubernetesThe claim — independent of any Pod (s2)
ephemeralA claim created and deleted with the PodThe Pod, but provisioned like persistent storage
HOSTPATH IS A HOLE IN THE WALL

A hostPath volume gives a container direct access to the node’s filesystem. Mount / or the container runtime’s socket and the container effectively owns the node. It also ties the Pod’s data to one machine. It is meant for node agents (Page IV, s5), and Pod Security (s9) forbids it for ordinary workloads.

A RAM-backed emptyDir is a tmpfs, and what you write there counts against the container’s memory limit — fill it and the container is OOM-killed.

s2. PersistentVolumes & Claims

Durable storage raises a separation-of-concerns problem. The developer writing a Pod spec knows they need 20 GiB of fast, single-writer storage. They don’t know — and shouldn’t have to know — whether that means an AWS EBS volume, a Ceph RBD image or an NFS export.

THE PROBLEM

If Pod specs referenced storage directly (awsElasticBlockStore: {volumeID: vol-0a1b…}), every manifest would be tied to one provider and one specific disk, and developers would need the permissions and knowledge to create disks.

THE SOLUTION

Split the request from the supply. A PersistentVolumeClaim says what is needed. A PersistentVolume describes a piece of real storage. Kubernetes binds one to the other.

🔐 Access Modes

ModeMeaning
ReadWriteOnce (RWO)Mounted read-write by one node — several Pods on that node can still share it
ReadWriteOncePod (RWOP)Mounted read-write by exactly one Pod in the cluster
ReadOnlyMany (ROX)Mounted read-only by many nodes
ReadWriteMany (RWX)Mounted read-write by many nodes — needs a shared filesystem such as NFS or CephFS

Block devices such as cloud disks support only the single-writer modes: a filesystem on a block device can’t safely be mounted by two kernels at once.

♻️ Reclaim Policy

When the claim is deleted, the PV moves to Released and its persistentVolumeReclaimPolicy decides what happens to the real storage:

  • Delete — the underlying disk is deleted too. The default for dynamically provisioned volumes.
  • Retain — the disk and PV are kept for an administrator to recover or clean up by hand. A released PV is never automatically bound to a new claim, since it still holds the old data.
DELETE MEANS DELETE

With the default policy, kubectl delete pvc destroys the data. For anything you can’t afford to lose, use a StorageClass with reclaimPolicy: Retain, or patch the PV’s policy after it is created. The pvc-protection finalizer from Page II, s4 only delays deletion while a Pod is using the claim.

s3. StorageClasses & Dynamic Provisioning

Pre-creating PVs by hand for every claim doesn’t scale. A StorageClass names a kind of storage and tells Kubernetes how to create volumes of that kind on demand.

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"   # used when a claim names no class
provisioner: ebs.csi.aws.com             # which CSI driver creates volumes (s4)
parameters:                              # opaque to Kubernetes, passed to the driver
  type: gp3
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer

When a claim names a class and no existing PV matches it, the driver behind the class creates a new volume, a PV is created for it, and the two are bound. Expanding a volume is a matter of editing the claim’s requested size, if the class allows it.

🗺️ Binding Mode and Topology

THE PROBLEM

With volumeBindingMode: Immediate, a disk is created the moment the claim appears — say in zone a. The Pod that uses it may later need a node in zone b, because that is where CPU is free. A zonal disk can’t attach across zones, so the Pod is stuck Pending.

THE SOLUTION

WaitForFirstConsumer. Provisioning waits until a Pod using the claim is scheduled. The scheduler picks the node first, and the volume is created in that node’s zone.

This is the scheduler’s volume filter from Page III, s3 in action: once a zonal volume exists, the Pod can only be placed in nodes of that zone.

s4. CSI: The Storage Plugin Contract

Storage drivers used to be compiled into Kubernetes itself, so adding or fixing one meant a Kubernetes release. The Container Storage Interface moved them out, the same way CRI moved out runtimes (Page I, s4) and CNI moved out networking (Page V, s4). A CSI driver is a gRPC server, run by the storage vendor in its own Pods.

🧱 Three gRPC Services

ServiceRunsKey calls
IdentityEverywhereGetPluginInfo, Probe
ControllerA Deployment, somewhere in the clusterCreateVolume, DeleteVolume, ControllerPublishVolume (attach), CreateSnapshot, ControllerExpandVolume
NodeA DaemonSet, on every nodeNodeStageVolume, NodePublishVolume, NodeUnpublishVolume

The driver knows nothing about Kubernetes objects. Translating between the two is done by standard sidecar containers shipped with it: external-provisioner watches claims, external-attacher watches VolumeAttachments, external-snapshotter and external-resizer handle snapshots and expansion, and node-driver-registrar registers the node plugin’s socket with the kubelet.

WHY STAGE AND PUBLISH ARE SEPARATE

Staging happens once per volume per node; publishing happens once per Pod. Two Pods on one node sharing an RWO volume get two bind mounts of a single staged mount, and the device is formatted and mounted only once.

THE MULTI-ATTACH ERROR

When a node dies, its RWO disk often stays attached to the dead VM. A replacement Pod on another node then fails with a multi-attach error until the old VolumeAttachment is cleaned up — the same “is it really gone?” problem as StatefulSets on Page IV, s4, seen from the storage side.

s5. Volume Snapshots

Snapshot support follows exactly the claim/volume split from s2, with one object for the request and another for the real thing. The API ships as custom resources plus a snapshot controller that a cluster installs separately; the driver does the work through CreateSnapshot.

apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: data-db-0-before-upgrade
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: data-db-0
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-db-0-restored
spec:
  storageClassName: fast
  dataSource:                          # restore: provision a new volume from the snapshot
    apiGroup: snapshot.storage.k8s.io
    kind: VolumeSnapshot
    name: data-db-0-before-upgrade
  accessModes: [ReadWriteOnce]
  resources: {requests: {storage: 20Gi}}
THE PROBLEM

A snapshot of a running database’s disk captures whatever blocks were on disk at that instant — possibly mid-write, with recent changes still in the database’s memory. It is crash-consistent: as if the power had been cut.

THE SOLUTION

For an application-consistent snapshot, quiesce the application first — flush and briefly freeze writes, or use the database’s own backup mode — then snapshot, then resume. Kubernetes doesn’t do this for you; backup tools and operators do.

A SNAPSHOT IS NOT A BACKUP

Snapshots usually live in the same storage system, region and account as the volume. Losing that system, or an attacker with that account’s credentials, loses both. A backup also needs a copy somewhere independent — and it needs the Kubernetes objects too: the claim, the StatefulSet, the Secrets, without which restored data has nothing to run it.

Module II — Config & Security

s6. ConfigMaps & Secrets

An image should be the same artifact in every environment. What differs — database host, feature flags, credentials — has to be injected at runtime.

THE PROBLEM

Baking configuration into images means one image per environment and a rebuild for every setting change. Putting credentials into images or Pod specs spreads them into registries, Git history and every log that prints a manifest.

THE SOLUTION

Store configuration as separate API objects — ConfigMaps for ordinary settings, Secrets for sensitive ones — and project them into Pods as environment variables or files.

apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  LOG_LEVEL: info
  app.yaml: |
    cache:
      ttlSeconds: 300
---
# in the Pod spec
containers:
- name: web
  envFrom:
  - configMapRef: {name: web-config}            # every key becomes an env var
  volumeMounts:
  - {name: config, mountPath: /etc/web}         # every key becomes a file
volumes:
- name: config
  configMap: {name: web-config}

🔄 What Happens When the ConfigMap Changes

Consumed asAfter an update
Environment variablesNever updated — read once at container start
VolumeFiles updated in place, typically within a minute or so
Volume with subPathNever updated

Even updated files only help if the application rereads them. The common pattern is to make configuration effectively immutable: put a hash of the config in the Pod template’s annotations, so any change produces a new template and a normal rolling update (Page IV, s3). Marking a ConfigMap or Secret immutable: true also lets kubelets stop watching it, which reduces API server load in large clusters.

🔑 What a Secret Is — and Isn’t

A Secret has the same shape as a ConfigMap, with values base64-encoded. Base64 is an encoding, not encryption: anyone who can read the object can read the value. What a Secret adds is a set of separate handling rules:

  • RBAC can grant ConfigMap access without Secret access (s8).
  • Secret volumes are written to a tmpfs on the node, never to its disk.
  • A kubelet is only allowed to read Secrets used by Pods scheduled to its own node.
  • The API server can encrypt Secrets at rest in etcd.
PLAINTEXT IN ETCD BY DEFAULT

Unless the API server is configured with an EncryptionConfiguration, Secrets are stored in etcd unencrypted, and so are etcd backups. Production clusters should enable encryption at rest, ideally through a KMS provider so the key itself lives outside the cluster. Many teams go further and keep the real secret in an external manager (Vault, a cloud secret store), syncing or mounting it at runtime.

s7. Identity: Users & ServiceAccounts

Page II, s8 showed authentication establishing who is calling. Kubernetes recognises two kinds of caller, and treats them very differently.

UsersServiceAccounts
ForHumans and external systemsWorkloads running in Pods
Stored as an object?No — a name vouched for by a certificate or identity providerYes — a namespaced ServiceAccount object
CredentialsClient certificates, OIDC tokensShort-lived tokens issued by the API server
UsernameWhatever the authenticator sayssystem:serviceaccount:<ns>:<name>

Every namespace gets a ServiceAccount named default, and every Pod runs as some ServiceAccount — default unless it names another.

🎫 Bound Service Account Tokens

THE PROBLEM

Service account tokens used to be long-lived credentials stored in Secrets. One leaked from a log or a compromised Pod worked forever, from anywhere, against any service that accepted it.

THE SOLUTION

Bound tokens from the TokenRequest API. The kubelet requests a token for each Pod, valid for a limited time, for a specific audience, and tied to that Pod — deleting the Pod invalidates it. The kubelet rotates it before it expires.

# mounted automatically, as a projected volume, in every Pod
/var/run/secrets/kubernetes.io/serviceaccount/
├── token        # a short-lived JWT, rotated by the kubelet
├── ca.crt       # to verify the API server
└── namespace

# a token for some other audience, e.g. an external service
volumes:
- name: vault-token
  projected:
    sources:
    - serviceAccountToken:
        audience: vault
        expirationSeconds: 3600
        path: token
IDENTITY BEYOND THE CLUSTER

The API server publishes the keys that sign these tokens through a standard OIDC discovery endpoint. External systems — cloud IAM, Vault — can therefore verify a Pod’s token without sharing any secret, and exchange it for their own credentials. This is how cloud “workload identity” features work: no static cloud keys in the cluster at all.

Most Pods never call the Kubernetes API. For those, automountServiceAccountToken: false removes a credential an attacker could otherwise steal.

s8. RBAC

Once a caller is identified, Role-Based Access Control decides what it may do. RBAC is built from two kinds of object: roles, which list permissions, and bindings, which grant a role to subjects.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: {name: deployer, namespace: shop}
rules:
- apiGroups: [apps]
  resources: [deployments]
  verbs: [get, list, watch, update, patch]
- apiGroups: [""]                      # "" is the core group
  resources: [pods]
  verbs: [get, list, watch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: {name: ci-deployer, namespace: shop}
subjects:
- {kind: ServiceAccount, name: ci-deployer, namespace: shop}
roleRef: {apiGroup: rbac.authorization.k8s.io, kind: Role, name: deployer}

🧭 Roles and Scope

ObjectDefines or grantsScope
RolePermissionsOne namespace
ClusterRolePermissionsReusable anywhere; also covers cluster-scoped resources
RoleBindingA Role or ClusterRole to subjectsOnly in the binding’s namespace
ClusterRoleBindingA ClusterRole to subjectsEvery namespace, plus cluster-scoped resources

Binding a ClusterRole with a RoleBinding is the common way to reuse one definition per namespace: the built-in view, edit and admin ClusterRoles are meant to be used exactly like that.

➕ RBAC Is Purely Additive

There are no deny rules. A request is allowed if any binding grants it. Removing access means removing a binding, never adding one, and you can’t grant a namespace’s edit role “except Secrets”. You also can’t grant permissions you don’t have yourself: creating a role with more power than you hold, or binding one, is refused unless you have the special escalate or bind verbs.

kubectl auth can-i delete pods -n shop --as=system:serviceaccount:shop:ci-deployer
kubectl auth can-i --list -n shop --as=alice
PERMISSIONS THAT ARE BIGGER THAN THEY LOOK

create pods in a namespace lets you start a Pod that runs as any ServiceAccount there and mounts any Secret there — so it is effectively all of their permissions. list secrets returns full values, not just names. Wildcards (*) grant every resource, including ones that will be added in future. Audit these first.

THE NODE AUTHORIZER

Kubelets aren’t governed by ordinary RBAC roles. A dedicated Node authorizer, together with the NodeRestriction admission plugin, limits each kubelet to its own Node object, the Pods bound to it, and the Secrets and ConfigMaps those Pods use. One compromised node can’t read every Secret in the cluster.

s9. Pod Security & Admission Policy

RBAC answers “may you create this Pod?” It says nothing about what kind of Pod. Someone allowed to create Pods could create one that is privileged, shares the host’s network and PID namespaces and mounts / through a hostPath — a container in name only, with full control of the node.

🔒 securityContext

Each Pod and container can tighten the isolation from Page I:

securityContext:                     # container level
  runAsNonRoot: true                 # refuse to start if the image runs as UID 0
  allowPrivilegeEscalation: false    # setuid binaries can't gain privileges
  readOnlyRootFilesystem: true       # writes only to declared volumes
  capabilities:
    drop: [ALL]                      # no raw sockets, no chown, no mount...
  seccompProfile:
    type: RuntimeDefault             # block rarely needed, dangerous syscalls

📏 Pod Security Standards

Kubernetes defines three standard profiles, and a built-in admission controller, Pod Security Admission, enforces them per namespace through labels.

ProfileAllowsFor
privilegedEverythingSystem and node-agent namespaces
baselineBlocks known privilege escalations: privileged mode, host namespaces, hostPath, extra capabilitiesOrdinary workloads with minimal changes
restrictedAlso requires non-root, no privilege escalation, dropped capabilities, a seccomp profileSecurity-sensitive workloads; the target for new apps
 
kubectl label namespace shop \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted

Running warn and audit one level stricter than enforce shows what would break before you tighten it: offending Pods are still admitted, but kubectl prints a warning and the audit log records it. Pod Security Admission replaced the older PodSecurityPolicy, which was removed from Kubernetes.

📜 Custom Policy with CEL

For rules the standard profiles don’t cover, ValidatingAdmissionPolicy runs in the validating admission stage from Page II, s8. Rules are written in CEL and evaluated inside the API server — no webhook to deploy, keep available or secure.

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata: {name: images-from-our-registry}
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - {apiGroups: [""], apiVersions: [v1], operations: [CREATE, UPDATE], resources: [pods]}
  validations:
  - expression: >-
      object.spec.containers.all(c, c.image.startsWith('registry.example.com/'))
    message: "Images must come from registry.example.com"
# a ValidatingAdmissionPolicyBinding then selects which namespaces it applies to
DEFENCE IN LAYERS

Each layer on this page covers a gap in another. Authentication says who you are; RBAC says which objects you may touch; admission policy says what those objects may contain; securityContext and Pod Security limit what the resulting process can do to the node; NetworkPolicy (Page V, s9) limits what it can reach. None of them is enough alone.
