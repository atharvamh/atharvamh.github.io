Kubernetes Notes

Workloads & Scheduling

The Pod as the unit everything else is built from, the controllers that manage Pods for stateless, stateful, per-node and run-to-completion work, and how the scheduler and the kernel decide where Pods run and what they may consume.

Module I — Workloads

s1. The Pod: The Atomic Unit

Kubernetes never schedules a container on its own. The smallest thing it places, starts and stops is a Pod: one or more containers that always land on the same node and share some of their namespaces (Page I, s1).

THE PROBLEM

Some processes belong together: a web server and the agent that ships its logs, or an app and a proxy that terminates its TLS. Packed into one container they can’t be built, versioned or restarted independently. Scheduled as separate containers, they might land on different machines.

THE SOLUTION

A group of containers with a shared fate. A Pod’s containers are co-scheduled, share one network identity and can share volumes, but each keeps its own image, filesystem and resource limits.

⏸️ The Pause Container

When the kubelet creates a Pod, the runtime first starts a tiny pause container whose only job is to exist. It creates and holds the Pod’s shared namespaces; the CNI plugin attaches the network to them; every other container joins them. App containers can then crash and restart without the Pod losing its IP. In CRI terms, this is the Pod sandbox.

🧩 Container Roles in a Pod

  • App containers — the main workload. All of them start together.
  • Init containers — run one at a time, in order, each to completion, before any app container starts. Used for migrations, waiting on a dependency, or fetching config.
  • Sidecar containers — helpers that run alongside the app: proxies, log shippers. Kubernetes now models them natively as init containers with restartPolicy: Always, so they start before the app and stop after it.
ONE POD, ONE INSTANCE

A Pod is one instance of something, never a way to scale it. Running three web servers means three Pods, each with one web container, not one Pod with three. Scaling is a controller’s job (s3).

s2. Pod Lifecycle & Probes

🔄 Phases and Container States

Pod phaseMeaning
PendingAccepted, but not all containers are running: waiting to be scheduled, pulling images, mounting volumes
RunningBound to a node; at least one container is running or restarting
SucceededAll containers exited successfully and won’t be restarted
FailedAll containers have terminated, at least one unsuccessfully
UnknownThe Pod’s state can’t be obtained — usually its node is unreachable

The phase is a coarse summary. The detail lives in each container’s state (Waiting, Running, Terminated) and its reason — ImagePullBackOff, CrashLoopBackOff, OOMKilled.

CRASHLOOPBACKOFF IS A DELAY, NOT AN ERROR

When a container keeps exiting, the kubelet restarts it with an exponentially growing delay — 10 s, 20 s, 40 s — capped at five minutes, and resets the delay once the container has run cleanly for a while. The reason for the crash is in kubectl logs --previous, not in the status.

🩺 Three Probes, Three Questions

ProbeQuestionOn failure
startupHas the app finished starting?Keeps waiting; the other probes are held off until it passes. Restarts the container if it never does.
livenessIs the process stuck beyond recovery?Kills and restarts the container
readinessShould this Pod get traffic right now?Removes the Pod from Service endpoints; no restart
 
readinessProbe:
  httpGet: {path: /ready, port: 8080}
  periodSeconds: 5
livenessProbe:
  httpGet: {path: /healthz, port: 8080}
  periodSeconds: 10
  failureThreshold: 3        # 3 consecutive failures → restart
THE PROBLEM

A liveness probe that checks a downstream dependency — the database is slow, so /healthz fails — restarts every replica at once. The restarts add load, the dependency gets slower, and the outage spreads.

THE SOLUTION

Liveness checks only the process itself. Dependency trouble belongs in readiness, which takes the Pod out of rotation without killing it.

🛑 Graceful Termination

Deleting a Pod starts two independent processes at the same moment, and they race.

  1. The API server sets deletionTimestamp. The Pod shows Terminating.
  2. In parallel: the EndpointSlice controller removes the Pod from its Services, and the kubelet starts shutting it down.
  3. The kubelet runs the preStop hook if there is one, then sends SIGTERM to each container.
  4. When terminationGracePeriodSeconds (default 30) runs out, anything still running gets SIGKILL.

The common fix is a short preStop sleep, which gives the endpoint updates time to reach every node before the app stops accepting connections. The app itself must handle SIGTERM by draining in-flight work, not by exiting immediately.

s3. ReplicaSets & Deployments

A bare Pod that dies stays dead: nothing recreates it. Controllers turn Pods into something that heals.

🧬 ReplicaSet: Keep N Copies

A ReplicaSet has three things: a selector, a desired replica count, and a Pod template. Its reconcile loop is the simplest in Kubernetes: count the Pods matching the selector, create Pods from the template if there are too few, delete some if there are too many. It doesn’t care which Pods they are — any matching Pod counts, and a matching Pod without an owner is adopted.

🚀 Deployment: Change Versions Safely

A ReplicaSet can’t perform an upgrade: changing its template affects only Pods created afterwards. A Deployment manages ReplicaSets instead of Pods. Each distinct Pod template gets its own ReplicaSet, labelled with a hash of the template (pod-template-hash). A rollout is the Deployment controller scaling the new ReplicaSet up and the old one down.

FieldDefaultControls
maxSurge25%How many Pods above the desired count may exist during a rollout
maxUnavailable25%How many desired Pods may be unavailable during a rollout
revisionHistoryLimit10How many old, scaled-to-zero ReplicaSets to keep for rollback
progressDeadlineSeconds600How long without progress before the rollout is marked failed
 
kubectl set image deployment/web nginx=nginx:1.28   # new template → new ReplicaSet
kubectl rollout status deployment/web
kubectl rollout undo deployment/web                 # scale the previous ReplicaSet back up
ROLLBACK IS JUST ANOTHER ROLLOUT

The old ReplicaSet was never deleted, only scaled to zero, so rolling back copies its template into the Deployment and the same surge-and-drain process runs in reverse. The alternative strategy, Recreate, deletes every old Pod before creating new ones — for apps that can’t run two versions at once.

s4. StatefulSets

ReplicaSet Pods are interchangeable cattle: random names, any one replaceable by any other. A database replica isn’t. It has a role in its cluster, a data directory that belongs to it, and peers that address it by name.

THE PROBLEM

A three-node database needs each member to come back after a restart with the same name, the same network address and the same disk — and its peers must be able to find it before it starts serving.

THE SOLUTION

A StatefulSet gives each Pod a stable identity. Pods are numbered db-0, db-1, db-2; each keeps its ordinal, its DNS name and its own PersistentVolumeClaim across rescheduling.

🪪 What “Stable Identity” Means

  • Stable name — <statefulset>-<ordinal>. A replacement for db-1 is again called db-1.
  • Stable DNS — through a headless Service, each Pod gets its own record: db-1.db.default.svc.cluster.local.
  • Stable storage — volumeClaimTemplates create one PVC per ordinal (data-db-1). The replacement Pod reattaches to the same claim. Scaling down does not delete the claims by default.
  • Ordering — by default Pods start one at a time, db-0 first, each waiting for the previous to be ready; they are removed in reverse order.

☝️ At Most One

The strongest guarantee a StatefulSet makes is that there is never more than one Pod with a given identity. Two Pods both believing they are db-0, writing to the same volume or both accepting writes as leader, is split-brain — the worst failure a stateful system can have.

That guarantee explains the behaviour from Page III, s7. When a node becomes unreachable, the control plane can’t tell whether db-0 is dead or still running behind a network partition. So the old Pod object stays in place, stuck in Terminating, and the StatefulSet controller will not create a new db-0 until it is confirmed gone.

RELEASING A STUCK STATEFULSET POD

Once you know the node is really down, either delete the Node object, apply the node.kubernetes.io/out-of-service taint to it, or force-delete the Pod with --grace-period=0 --force. Each tells Kubernetes “I promise the old one is gone” — if it isn’t, you have created the split-brain the StatefulSet was protecting you from.

A StatefulSet provides identity and ordering, not replication. It does not know what a primary is, how to fail over, or how to back up. That knowledge lives in the database itself or in an operator (Page VII).

s5. DaemonSets, Jobs & CronJobs

🛰️ DaemonSet: One per Node

Some software must run on every node because it serves the node itself: log collectors, monitoring agents, CNI plugins, storage drivers. A DaemonSet’s desired state is “one Pod on every node that matches” — add a node and a Pod follows; remove a node and its Pod goes with it.

The DaemonSet controller creates one Pod per node with a node affinity pinning it there, and the regular scheduler places it. DaemonSet Pods automatically tolerate taints such as not-ready and unreachable, because a node agent must keep running exactly when a node is unhealthy.

🏁 Job: Run to Completion

Deployments assume a process should run forever, and restart it whenever it exits. A Job inverts that: its desired state is a number of successful completions.

apiVersion: batch/v1
kind: Job
metadata:
  name: resize-images
spec:
  completions: 10          # succeed 10 times in total
  parallelism: 3           # at most 3 Pods at once
  backoffLimit: 6          # give up after 6 failed attempts (the default)
  ttlSecondsAfterFinished: 3600
  template:
    spec:
      restartPolicy: OnFailure   # Jobs may not use Always
      containers:
      - name: worker
        image: registry.example.com/resizer:2.1

With completionMode: Indexed, each Pod receives an index from 0 to completions − 1, so a batch can be split into deterministic shards.

⏰ CronJob: Jobs on a Schedule

A CronJob is a controller that creates a Job from a template according to a cron expression. The interesting field is what to do when the previous run hasn’t finished:

concurrencyPolicyWhen the previous Job is still running
Allow (default)Start another one alongside it
ForbidSkip this run
ReplaceStop the old Job and start the new one
PICKING THE CONTROLLER

Ask what “done” means. Never done and interchangeable: Deployment. Never done with identity: StatefulSet. Never done, one per node: DaemonSet. Done after N successes: Job. Done on a schedule: CronJob.

Module II — Scheduling & Resources

s6. Requests, Limits & QoS

Every container can declare two numbers per resource, and they do completely different jobs.

resources:
  requests:
    cpu: 250m        # a quarter of a CPU
    memory: 256Mi
  limits:
    cpu: "1"
    memory: 512Mi
  • Requests are a reservation used for placement. The scheduler only puts a Pod on a node whose unrequested capacity covers it. Nothing stops a container from using more than its request.
  • Limits are a ceiling enforced on the node by the kernel. The scheduler ignores them.

📐 How the Scheduler Counts

A node advertises allocatable capacity: its total CPU and memory minus what is reserved for the operating system, the kubelet and eviction headroom. A Pod fits if the sum of the requests of the Pods already on the node, plus this Pod’s requests, stays within allocatable. Actual usage plays no part in the decision.

THE PROBLEM

Requests set too low pack too many Pods onto a node; when they all use what they really need, the node runs out of memory. Requests set too high leave nodes half-idle while new Pods sit Pending.

THE SOLUTION

Set requests from measured usage, typically a high percentile of real consumption, and revisit them. The Vertical Pod Autoscaler (Page VII) automates exactly this.

🎚️ Quality of Service Classes

From the requests and limits of all its containers, every Pod is assigned a QoS class. The class decides who suffers first when a node runs short of memory.

ClassConditionUnder memory pressure
GuaranteedEvery container sets CPU and memory requests equal to limitsLast to be killed or evicted
BurstableAt least one request or limit set, but not GuaranteedIn between, ranked by usage above requests
BestEffortNo requests or limits anywhereFirst to be killed or evicted

The kubelet implements this partly through the kernel: it sets each container’s OOM score so the kernel’s OOM killer prefers BestEffort processes, and partly through its own eviction ranking (s8).

THE CPU LIMIT DEBATE

Because CPU is compressible, many teams set CPU requests but no CPU limits: the request still guarantees a fair share under contention, and the Pod can use idle CPU instead of being throttled while it sits unused. Memory limits are a different matter — without one, a leaking container can push the whole node into memory pressure.

s7. Placement Rules

Resource fit is only the first filter. Several mechanisms let you shape where Pods land, and they divide into two directions: the Pod choosing nodes, and nodes repelling Pods.

🧲 The Pod Chooses: Node Affinity

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:     # hard rule
      nodeSelectorTerms:
      - matchExpressions:
        - {key: kubernetes.io/arch, operator: In, values: [arm64]}
    preferredDuringSchedulingIgnoredDuringExecution:    # soft preference, weighted
    - weight: 50
      preference:
        matchExpressions:
        - {key: node.kubernetes.io/instance-type, operator: In, values: [m7g.large]}

“Required” rules act in the filter stage; “preferred” ones add to a node’s score. The suffix IgnoredDuringExecution means the rule is checked only at scheduling time: relabel the node later and running Pods stay put. The simpler nodeSelector field is an exact-match-only version of the required rule.

👥 Relative to Other Pods: Pod Affinity & Anti-Affinity

Pod affinity places a Pod near Pods with certain labels; anti-affinity keeps it away from them. “Near” is defined by a topologyKey — a node label whose value defines a domain.

topologyKey“Same domain” meansTypical use
kubernetes.io/hostnameSame nodeKeep replicas on separate machines
topology.kubernetes.io/zoneSame availability zoneSurvive a zone outage; keep chatty services close

⚖️ Topology Spread Constraints

Anti-affinity is all-or-nothing: “never two on one node” breaks down as soon as you have more replicas than nodes. Spread constraints express balance instead:

topologySpreadConstraints:
- maxSkew: 1                               # zones may differ by at most 1 Pod
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule         # or ScheduleAnyway, as a soft preference
  labelSelector:
    matchLabels: {app: web}

🚫 The Node Repels: Taints & Tolerations

Affinity is opt-in by the Pod. A taint is the reverse: a mark on a node that repels every Pod unless the Pod carries a matching toleration.

kubectl taint nodes gpu-1 dedicated=gpu:NoSchedule

# in the Pod spec
tolerations:
- {key: dedicated, operator: Equal, value: gpu, effect: NoSchedule}
EffectNew Pods without a tolerationPods already running
PreferNoScheduleAvoided if possibleUnaffected
NoScheduleNever placed hereUnaffected
NoExecuteNever placed hereEvicted, after tolerationSeconds if set
TOLERATING IS NOT ATTRACTING

A toleration only permits a Pod onto a tainted node; it doesn’t draw it there. Dedicating GPU nodes to GPU work takes both halves: a taint so nothing else lands there, and node affinity so the GPU Pods go nowhere else. The node-failure eviction on Page III, s7 is this same mechanism, driven by the unreachable:NoExecute taint.

s8. Priority, Preemption & Eviction

When there isn’t enough room for everything, something must decide what runs. Kubernetes has three distinct mechanisms, and they are easy to confuse.

🥇 Priority and Preemption

A PriorityClass attaches a number to Pods. When a high-priority Pod can’t be scheduled anywhere, the scheduler looks for a node where evicting some lower-priority Pods would make it fit, evicts them, and records the chosen node in the Pod’s status.nominatedNodeName.

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: business-critical
value: 100000
description: "Customer-facing services"

Two built-in classes, system-cluster-critical and system-node-critical, sit far above anything you should define. They keep DNS, networking and other cluster components from being preempted by workloads.

🛡️ PodDisruptionBudgets

Voluntary disruptions — draining a node for an upgrade, the autoscaler removing a node — should never take down too many replicas at once. A PodDisruptionBudget sets the floor:

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web
spec:
  minAvailable: 3          # or maxUnavailable: 1
  selector:
    matchLabels: {app: web}

kubectl drain removes Pods through the Eviction API, which checks the budget and refuses an eviction that would break it. The drain waits and retries until the Deployment has created replacements elsewhere.

🌡️ Node-Pressure Eviction

Independently of the scheduler, each kubelet protects its own node. When available memory, disk or inodes cross an eviction threshold, the kubelet evicts Pods to reclaim them, ranking candidates by whether they use more than they requested, then by priority, then by how far over their request they are.

MechanismTriggered byRespects PDBs
PreemptionScheduler, to place a higher-priority PodBest effort — tries to, but may violate them
API-initiated evictionkubectl drain, autoscalers, operatorsYes — refused if it would break the budget
Node-pressure evictionkubelet, when a node runs short of resourcesNo — the node’s survival comes first
Node failureTaint-based eviction (Page III, s7)No — the disruption already happened
WHAT A PDB CAN’T DO

A PodDisruptionBudget guards only against voluntary disruptions that go through the Eviction API. It cannot prevent a node crash, an OOM kill or node-pressure eviction. Surviving those takes enough replicas, spread across failure domains (s7) — and requests honest enough that nodes don’t run out of memory in the first place (s6).
