Module I — Execution Model

s1. Redis as a Data Structure Server

Redis is widely used as a cache, but the design intent was broader: a data structure server. Caching became the dominant use case because Redis's core properties — in-memory storage, fast lookups, rich types — happen to fit caching workflows perfectly.

Redis vs. Memcached

PropertyMemcachedRedis
Value typeOpaque blobTyped structure — string, hash, list, set, sorted set…
Server awarenessDumb store, no ops on valueServer understands and mutates types directly
Round-tripsFetch → deserialize → modify → serialize → storeSingle atomic server-side command (LPUSH, ZADD, HINCRBY)
Use-case fitSimple key/blob cacheCache, leaderboards, queues, pub/sub, rate limiting…
KEY INSIGHT

Because Redis understands the value type, operations happen on the server atomically. You don't round-trip data to the client just to modify it.

s2. Single-Threaded Execution Model

Redis command execution is single-threaded. This is a deliberate design choice, not a limitation.

Why Single-Threaded Works

For in-memory operations, the bottleneck is never CPU execution — a hash lookup takes nanoseconds. The real bottleneck is the network round-trip (microseconds). Since CPU isn't the constraint, adding threads for execution would only introduce lock contention without improving throughput.

RAM access ~100ns  →  command execution (hash lookup etc.) ~few hundred ns  →  network round-trip ~100µs–1ms

Network dominates. Single-threaded execution is free atomicity at nearly zero cost.

What single-threading gives you

Every command is atomic by construction — no locks needed. The moment you parallelize execution, every compound operation requires synchronization. Redis avoids this entirely by processing one command at a time: command B cannot start until command A is completely finished.

Sequential execution — free isolation

Because the main thread processes commands sequentially, no two commands can ever interleave. No client ever observes a half-finished state.

Client 1: INCR counter
Client 2: INCR counter

Redis main thread:
  INCR (client 1) → read 5, write 6   ← completes fully first
  INCR (client 2) → read 6, write 7   ← only then this starts
  Result: counter = 7  ✓

Multi-threaded system without locks:
  Thread 1 reads 5
  Thread 2 reads 5    ← interleaved, both saw 5
  Thread 1 writes 6
  Thread 2 writes 6   ← overwrites thread 1's result
  Result: counter = 6  ✗  one increment lost

Atomic means indivisible — not success/fail

Two different definitions of "atomic" are often conflated:

TypeMeaningRedis?
Indivisible atomicExecutes as one uninterruptible unit — no command can observe a half-finished stateAlways guaranteed
ACID atomic (all-or-nothing)If any step in a transaction fails, all previous steps roll backNot supported

Redis guarantees isolation — commands never interleave. Redis does not guarantee rollback — if a command fails partway, prior steps are not undone. Two different properties, commonly conflated under one word.

Where this matters — MULTI/EXEC vs. Lua

MechanismAtomicityRollback on failure
MULTI/EXECAll queued commands execute without interruptionNo — if command 2 of 5 errors, 1, 3, 4, 5 still run
Lua scriptEntire script runs as one uninterruptible block, invisible to other clientsNo rollback, but no partial state leaks out either

Lua scripts are the stronger primitive — the whole script is invisible to other clients while executing. MULTI/EXEC gives non-interleaving, but not error recovery.

What the main thread actually does

A Redis command on the main thread is almost always: READ from RAM → compute → WRITE to RAM.

CommandRAM readComputeRAM write
GET fooHash lookup → value—None
SET foo barHash lookup → slot—Write new value
INCR counterRead integer+1Write back
LPUSH list aFind list headPrepend nodeUpdate pointer

Compute is trivial — a few arithmetic ops, a pointer follow, a comparison. The dominant cost is the RAM access itself.

Why RAM access has a cost — the cache hierarchy

RAM is not uniformly fast. The CPU has a hierarchy of caches — smaller and faster closer to the core, larger and slower further away.

LevelLatencySizeScope
L1 cache~1ns~32KBPer CPU core
L2 cache~4ns~256KBPer CPU core
L3 cache~10nsFew MBShared across cores
RAM (DRAM)~100nsGigabytesFull system

A hot key recently accessed lives in L1/L2 — lookup is ~1–4ns. A cold key sitting in DRAM costs ~100ns. This is why Redis's listpack encoding (contiguous memory) matters — sequential access stays in CPU cache lines, avoiding expensive DRAM round trips for small collections.

FULL COST PICTURE PER COMMAND

Network I/O ~100µs — dominant cost. RAM access ~1–100ns — hot key vs. cold key. Compute ~1–10ns — arithmetic, pointer follows. The main thread's job is RAM reads and writes; everything expensive — network, disk — happens outside it. That's the whole point of the design.

Event loop — not one thread per connection

Redis uses epoll/kqueue to multiplex thousands of client connections onto a single event loop. It is not one OS thread per client — this is why Redis sustains 100k+ ops/sec on a single thread.

s3. Network I/O Threading (Redis 6+)

At high connection counts, reading bytes off sockets and writing responses became the actual bottleneck — not command execution. Redis 6 added I/O threads to parallelize exactly this, while keeping the execution model intact.

Request Flow

Client Request
     │
     ▼
I/O Threads        ← read bytes off socket, parse RESP protocol
     │
     ▼
Main Thread        ← execute command against in-memory data (sequential)
     │
     ▼
I/O Threads        ← serialize response, write bytes back to socket
     │
     ▼
Client Response

Clean separation: I/O threads own the wire, the main thread owns the data. They never share data structures — no locks anywhere in the hot path.

Coordination Without Locks

This is not a typical thread pool with a shared concurrent queue. Redis uses two specific primitives — dedicated per-thread lists and an atomic counter — to coordinate without locks.

Dedicated lists — no shared queue contention

In a standard thread pool, a shared queue sits in the middle — every push and pull needs a lock or CAS operation, and threads contend under load. Redis avoids this: each I/O thread has its own private client list, assigned directly by the main thread. No two threads ever touch the same list simultaneously.

Standard thread pool (what Redis does NOT do):
Main Thread → pushes work → [shared queue] → worker threads pull
                                ↑ lock contention here

Redis (dedicated lists):
Main Thread
├── client A, B → I/O Thread 1's list  (only Thread 1 reads this)
├── client C, D → I/O Thread 2's list  (only Thread 2 reads this)
└── client E    → I/O Thread 3's list  (only Thread 3 reads this)

Atomic counter — the synchronization signal

After assigning all clients, the main thread needs to know when all I/O threads are done. It uses a single shared atomic integer — lock-free, handled at the CPU instruction level, no kernel involvement.

Main thread sets counter = 3   (number of active I/O threads)

I/O Thread 1 finishes → counter-- → 2
I/O Thread 2 finishes → counter-- → 1
I/O Thread 3 finishes → counter-- → 0

Main thread sees 0 → all done, proceed to command execution

Busy-Polling vs. Blocking

Two ways to wait for that counter to reach zero:

ApproachMechanismCost
Blockingpthread_cond_wait() — kernel sleeps the thread, wakes it on signal2 kernel context switches, ~1–10µs each
Busy-pollingwhile (counter != 0) {} — spins in userspace checking the counterCPU cycles burned spinning, zero kernel involvement

What a context switch actually is

A CPU core runs one thread at a time. The kernel is the traffic controller — when it swaps one thread out for another, that's a context switch. It's expensive because the kernel must save the entire state of the outgoing thread (registers, stack pointer, program counter) and restore the incoming one.

CPU core (one thread at a time):

t=0   Thread A running  ──────────┐
t=1   kernel swaps                │ ← context switch (~1–10µs)
t=2   Thread B running  ──────────┘

When the main thread calls pthread_cond_wait(), it tells the kernel: "take me off the CPU, wake me when an I/O thread signals me." Two context switches happen — one to sleep, one to wake.

Main thread calls pthread_cond_wait()
        │
        ▼
Kernel saves main thread state → moves it off CPU    ← context switch #1
        │
Kernel puts another thread on CPU (other work)
        │
I/O Thread finishes → calls pthread_cond_signal()
        │
        ▼
Kernel saves current thread → restores main thread   ← context switch #2
        │
        ▼
Main thread resumes
I/O thread finishes at t=0µs

Condition variable: main thread wakes at t=5µs  (kernel round trip)
Busy-poll:          main thread exits at t=0µs  (sees counter hit 0 immediately)
PTHREAD_COND_WAIT

You go to the break room and ask someone to fetch you when the task is done. Relaxed, but there's a delay between them finishing and you getting back to your desk.

BUSY-POLLING

You stand behind their chair, watching the screen. Wasteful — but the instant they finish, you're moving. No delay.

Redis stands behind the chair — because in its world, the walk to the break room takes longer than the task itself. Its latency target is microseconds, and a context switch costs 1–10µs: the same order of magnitude as the entire operation. That tradeoff only makes sense at microsecond scale — you would not busy-poll if threads needed to wait seconds.

Main Thread
├── assigns clients → I/O Thread 1's list
├── assigns clients → I/O Thread 2's list
└── assigns clients → I/O Thread 3's list
        │
        ▼  I/O threads read sockets in parallel
        │
Main Thread busy-polls atomic counter until 0
        │
        ▼
Main Thread executes all queued commands sequentially (single-threaded)
        │
        ▼
Main Thread assigns responses back to I/O thread lists
        │
        ▼
I/O threads write responses to sockets in parallel
RESP PARSING HAPPENS IN I/O THREADS

I/O threads don't just move raw bytes — they parse the Redis Serialization Protocol (RESP). The main thread receives clean, structured command objects and never touches wire bytes.

WHY NOT FULLY MULTI-THREAD EXECUTION?

Because single-threaded execution is what preserves atomicity. Parallelizing execution would require locks on every shared data structure — trading simplicity and correctness for marginal CPU gains on a workload that was never CPU-bound.

s4. Event Loop Internals — ae & Per-Client Buffers

Redis implements its own event loop, called ae (async events), in ae.c. It's a thin abstraction over the OS-level I/O multiplexing primitive — epoll on Linux, kqueue on macOS. Two categories of events run on the same loop.

Event typeWhat triggers itExamples
File eventsA socket fd becomes readable or writableClient sends command, response ready to flush
Time eventsA timer firesActive key expiry, replication heartbeat, cluster gossip

The Core Loop

File events and time events are fundamentally different mechanisms sharing the same dispatch path:

while (running) {
    epoll_wait(timeout=100ms) // block until fd ready OR 100ms elapses
    aeProcessFileEvents()     // dispatch readable/writable handlers
    aeProcessTimeEvents()     // run any due timers
}
Wake-up triggerDriven byLatencyExamples
File eventKernel interrupt — fd becomes readySub-millisecondClient sends command, socket becomes writable
Time event100ms timeout expiresUp to 100msActive key expiry, replication heartbeat, cluster gossip

The 100ms is a fallback ceiling — not a polling interval

epoll_wait(timeout=100ms) means: wake immediately the moment any fd is ready; if nothing happens for 100ms, wake anyway just to run time events, then block again. Polling would mean waking every 100ms regardless — that isn't what Redis does. A busy server wakes on every client event, so the 100ms timeout rarely fires; an idle server wakes every 100ms purely for housekeeping, burning near-zero CPU.

Client sends command at t=5ms

Polling model (100ms tick):
  t=0ms   wake, nothing ready, sleep
  t=5ms   client sends ← nobody home
  t=100ms wake, process command    ← 95ms latency introduced

epoll_wait with 100ms timeout:
  t=0ms   epoll_wait blocks
  t=5ms   kernel interrupts immediately → command processed now
  t=100ms would have woken here, but already handled

After every epoll_wait return — kernel interrupt or timeout — Redis processes both file events first, then checks for fired timers. One loop, two event categories, single dispatch path. epoll_wait() is O(1) per event — the kernel doesn't scan every watched fd, it only returns the ones actually ready. That's why Redis can watch thousands of connections without degrading throughput.

Why Buffers Exist

The network and Redis don't operate at the same speed. A client can send a partial command across multiple TCP segments; Redis can have a response ready before the socket is writable. Buffers are the per-client holding zones that decouple these timing mismatches — every connected client gets its own read buffer and write buffer.

Read buffer — input side

When epoll_wait signals a fd is readable, Redis calls read() on the socket. TCP doesn't guarantee whole messages arrive together, so Redis accumulates bytes into a per-client read buffer until the parser finds a complete command.

Client sends across two TCP segments:
  Segment 1: "*2\r\n$3\r\nGET\r\n"
  Segment 2: "$5\r\nhello\r\n"

Read buffer accumulates both → parser finds complete command → execute
Consumed bytes removed from buffer front → partial bytes wait at back

The read buffer is a sliding window. Bytes arrive, the RESP parser consumes complete commands off the front, incomplete data waits at the back. The parser never blocks — if it can't find a complete command, it returns and waits for the next readable event.

Write buffer — output side

When execution completes, the response is ready — but the socket may not be writable yet (the kernel's send buffer might be full). Redis pushes the response into a per-client write buffer and waits for epoll to signal the fd is writable.

Command executes → response built → pushed to write buffer
                                          │
                              epoll signals fd writable
                                          │
                              writeToClient() drains buffer
                                          │
                              bytes → kernel socket send buffer
                                          │
                              kernel delivers bytes to client

If the write buffer drains completely in one shot, Redis removes the writable listener for that fd — no point watching it — and re-registers only when there's something new to write. This keeps epoll's watched fd set lean.

Full Request Lifecycle

① Client sends bytes over TCP
        │
② Kernel buffers in socket recv buffer, marks fd readable
        │  epoll_wait() returns
③ readQueryFromClient() reads bytes into READ BUFFER (per client)
        │
④ RESP parser scans read buffer
   complete command? → extract and execute
   partial command?  → wait for more bytes, return to loop
        │
⑤ Command executes against in-memory data (main thread, RAM)
        │
⑥ Response pushed to WRITE BUFFER (per client)
        │  epoll signals fd writable
⑦ writeToClient() drains write buffer → kernel socket send buffer
        │
⑧ Kernel delivers bytes to client
PER-CLIENT ISOLATION IS THE KEY GUARANTEE

Every client has its own read and write buffer. A slow client reading its response doesn't stall command execution for anyone else — its response simply waits in its write buffer. The single-threaded loop never blocks on one client's I/O.

BACKPRESSURE — SLOW CLIENT PROTECTION

If a client is extremely slow and its write buffer keeps growing unboundedly, Redis enforces hard limits. Exceed client-output-buffer-limit and Redis kills that client connection — a misbehaving or slow client cannot exhaust the server's memory.

OS Layer Summary

Syscall / primitiveRole in the event loop
epoll_create()Creates the epoll instance — the kernel's watched fd registry
epoll_ctl()Registers or removes fds from the watch list (add on connect, remove on disconnect)
epoll_wait()Blocks until watched fds are ready — returns only ready fds, O(1)
read()Reads bytes from socket into the per-client read buffer
write()Writes bytes from the per-client write buffer into the kernel socket send buffer
ONE-LINE SUMMARY

The read buffer decouples TCP fragmentation from command parsing. The write buffer decouples command execution from socket availability. Together they let a single-threaded event loop serve thousands of clients without ever blocking on I/O.

Dual Encoding — the Hidden Optimization

For small collections, Redis does not use the "real" data structure internally. It uses a compact flat encoding called listpack (formerly ziplist) — a contiguous byte array with no pointers. Cache-line friendly, with dramatically lower per-element memory overhead.

Encoding promotion — one-way

Compact encoding (listpack) is used while a collection is small (e.g. hash < 128 entries, entries < 64 bytes). It's promoted to the full data structure (hash table, skiplist) once that threshold is crossed. Promotion is automatic, transparent, and one-way — a promoted structure never reverts. Unlike a dynamic array such as List<T>, which just grows in place, Redis switches the underlying representation entirely.

Small hash (≤128 keys)       Large hash (>128 keys)
┌─────────────────────┐      ┌──────────────────────┐
│ listpack             │  →   │ hash table            │
│ [k1|v1|k2|v2|k3|v3] │      │ bucket[] → entry →   │
│ contiguous memory    │      │ next (chained)        │
└─────────────────────┘      └──────────────────────┘
  cache-friendly, zero         pointer overhead,
  pointer overhead              O(1) avg lookup
WHY THIS MATTERS

In production, a huge fraction of Redis keys are small. Listpack encoding means Redis memory efficiency is significantly better than a naive implementation — without any change to the API.

s6. Persistence — RDB & AOF

Redis is an in-memory store. If the server process dies, everything in RAM is lost — unless persistence is configured. Redis offers two complementary mechanisms.

RDB — Point-in-Time Snapshots

Periodically dumps the entire dataset to a binary file (dump.rdb), on a configurable trigger — e.g. "save if 1000+ keys changed in the last 300s." On restart, Redis loads the RDB file and reconstructs the full in-memory state.

t=0          t=300s       t=600s       t=750s (crash)
 │             │             │               │
 ▼             ▼             ▼               ✗
[snapshot]  [snapshot]  [snapshot]     ← 150s of writes lost
HOW RDB SNAPSHOTS AVOID BLOCKING

Redis calls fork(). The child process writes the snapshot to disk while the parent keeps serving requests. The OS uses copy-on-write — parent and child share memory pages until the parent modifies one, at which point only that page is copied. Consistent snapshot, zero blocking on the hot path.

AOF — Append-Only File

Every write command is appended to a log after it executes in memory. On recovery, Redis replays the entire log top to bottom to reconstruct state.

WAL PATTERN (POSTGRES)

write to log → ack client → apply to data. The log is written ahead of the data — hence "write-ahead."

AOF PATTERN (REDIS)

apply to RAM → ack client → append to log. RAM is updated first, the log written after — the opposite order.

AOF is not a WAL. It's better described as an operation log or command journal — a sequential record of every write command executed, used purely for recovery. The log is a recovery artifact, not the write path.

SET foo bar
INCR counter
LPUSH mylist a
HSET user:1 name "Alice"
...

Three fsync policies control the durability/performance tradeoff:

PolicyBehaviorMax data loss
alwaysfsync on every writeZero (theoretically)
everysec (default)fsync every second~1 second
noOS decides when to flushOS buffer worth

AOF rewrite — log compaction

AOF grows unboundedly — every version of every key is in there, but only the final state matters for recovery. A key updated a million times is a million log entries, but one line in a rewrite. Redis periodically rewrites the AOF by looking at current in-memory state and generating a brand-new minimal log representing exactly that state. The old AOF is never parsed — RAM is the source of truth.

Old AOF (bloated):          New AOF (after rewrite):
SET foo 1                   SET foo 5
SET foo 2                   SET counter 1000
SET foo 3                   HSET user:1 name alice age 30
SET foo 4
SET foo 5                   Three lines. Not a million.
SET counter 1
... (1000 more lines)

How rewrite runs without blocking — fork()

Parent  →  keeps serving writes
            ├── appends to OLD AOF        (safety if child crashes)
            └── buffers writes in rewrite buffer (RAM)

Child   →  iterates in-memory dataset
            └── writes new compact AOF to temp file
                      │
                      ▼  child signals done
Parent  →  appends rewrite buffer to new AOF
            ├── atomic rename(temp → aof.file)
            └── old AOF discarded
THE REWRITE BUFFER

Captures writes arriving during the rewrite window. Once the child finishes, the buffer is appended to the new file before the atomic rename — no writes are lost. New AOF = RAM snapshot (child) + rewrite buffer (parent). The child covers everything in RAM at fork time; the buffer covers every write between fork() and rename(). Together, complete and minimal — nothing missed, nothing redundant.

When rewrite triggers — both conditions must be true

ConfigDefaultMeaning
auto-aof-rewrite-percentage100AOF has doubled in size since the last rewrite
auto-aof-rewrite-min-size64mbAOF is at least this large

The min-size threshold prevents fork overhead on small AOFs, where compaction isn't worth it.

Production setup — both together

SetupRecovery speedData-loss risk
RDB onlyFast (binary load)Up to snapshot interval
AOF onlySlow on large datasets (replays all commands)~1 second (everysec)
RDB + AOFFast (load RDB, replay AOF delta only)~1 second
HONEST CAVEAT

Even with both enabled, Redis gives best-effort durability — not guaranteed durability. The design philosophy trades this for performance. Redis is not a source of truth; pair it with a durable store (Postgres, Cosmos DB) for data you cannot afford to lose.

The write() Path & fsync Internals

Two separate regions of RAM are involved in a write — often conflated:

Memory regionManaged byWhat lives here
Redis dataset memoryRedis (via jemalloc)The key-value data — hash tables, listpacks, skiplists. Updated on every command.
Kernel page cacheOS kernelAOF file bytes buffered before disk flush. Written when Redis calls write() on the AOF fd.

The page cache is carved into 4KB pages — the smallest unit the kernel uses to manage memory. When Redis appends to the AOF, the kernel finds the relevant page, updates it in RAM, and marks it dirty. The page cache itself can be gigabytes — it uses whatever RAM isn't claimed by processes.

Four-buffer journey — SET foo bar to disk

① Redis dataset (jemalloc RAM)
   hash table updated — the actual data lives here

② AOF write buffer (Redis-managed userspace RAM)
   command text "SET foo bar\r\n" batched here
   flushed once per event loop iteration via write()

③ Kernel page cache (kernel-managed RAM)
   4KB page updated, marked dirty
   write() returns to Redis immediately — nanoseconds

④ Disk controller buffer (hardware cache)
   fdatasync() forces kernel to flush dirty pages here

⑤ Physical storage (NAND flash / magnetic platter)
   data is now truly durable
fsync() VS. fdatasync()

fsync() flushes file data and metadata (size, modification time, inode) — two disk ops minimum. fdatasync() flushes file data only — one disk op. Redis uses fdatasync() because it doesn't care about timestamps, only that command bytes are durable — one fewer disk write per sync.

The fsync policies map directly to where in the chain Redis stops and waits:

PolicyStops atRisk if crash
alwaysStep ① — waits after every commandZero data loss
everysecStep ② — background thread syncs every 1sUp to 1s of acknowledged writes
noStep ① — kernel page cache, kernel decidesUp to 30s of writes

When the kernel flushes dirty pages

Without an explicit fdatasync(), the kernel uses three triggers:

TriggerConditionDefault
Age thresholdPage dirty longer than vm.dirty_expire_centisecs30 seconds
Background ratioDirty pages exceed vm.dirty_background_ratio — writeback starts quietly10% of RAM
Hard ratioDirty pages exceed vm.dirty_ratio — write() calls start blocking20% of RAM
THE HARD RATIO IS A PRODUCTION CONCERN

If Redis writes to AOF faster than the disk can keep up, dirty pages accumulate. Once they exceed 20% of RAM, the kernel forces write() calls to block until pages flush — Redis's event loop stalls, and latency spikes on write-heavy workloads with slow disks.

WAL Inversion — Redis vs. Postgres vs. Cosmos DB

SystemWrite orderClient ack timingDurability guarantee
PostgresWAL to disk first → then RAMAfter WAL fsyncAck = durable
RedisRAM first → AOF afterAfter RAM writeAck = in RAM only
Cosmos DB (strong)RAM + quorum replication → WAL on each replicaAfter quorum confirmsAck = durable across nodes

Postgres pays ~1–3ms per write waiting for WAL fsync. Redis pays ~100ns updating RAM — two to three orders of magnitude faster, at the cost of a durability window. Cosmos DB's durability comes from replication quorum across machines rather than local disk — even if one node's disk hasn't flushed, the data exists on other nodes.

Module III — Replication & High Availability

s7. Replication — Full & Partial Sync

Redis replication is primary → replica, asynchronous by default. The replica is a read-only copy — writes always go to the primary, replicas serve reads.

ASYNC TRADEOFF

The primary doesn't wait for replicas to acknowledge before confirming a write to the client. It can acknowledge a write, then crash before replication completes — that write is lost.

Primary Availability During Sync

The primary stays fully available for reads and writes during a full sync — the same fork() trick used by RDB snapshots. The child process streams the snapshot to the replica while the parent keeps serving requests normally. New writes during the sync window are buffered in the replication backlog and streamed once the replica finishes loading the RDB.

Primary
   │
   ├── fork() ──► Child streams RDB snapshot to replica
   │                   (seconds for large datasets)
   │
   └── Parent keeps serving reads + writes
              ↓
         buffers new writes in replication backlog

Full sync — PSYNC

Triggered on first connect, or when a replica has fallen too far behind. The replica sends PSYNC ? -1. The primary forks, generates an RDB snapshot, streams it — then, once loaded, replays the backlog delta to bring the replica to present state.

Partial sync — the ring buffer

Every primary maintains two tracking values and a buffer:

ConceptWhat it is
Replication IDA unique identity string for this primary's dataset lineage — like a UUID for the command history
Replication offsetA monotonically increasing byte counter, incrementing with every byte streamed — a cursor into the command stream
Replication backlogA fixed-size circular ring buffer of recent write commands. Default 1MB — new writes overwrite the oldest entries once full
 
Replication backlog (ring buffer, e.g. 1MB)

oldest surviving         current primary
     offset                   offset
        │                        │
        ▼                        ▼
[...commands........commands........commands]
        ↑
  gets overwritten as new writes arrive

On reconnect after a brief disconnect, the replica says: "my replication ID is X, and I was at offset N — give me everything after N." The primary checks whether offset N is still inside the ring buffer.

Replica last offset: 3000
Backlog window:      5000 → 9000 (current)

3000 < 5000 → offset overwritten → full sync required

─────────────────────────────────────────────

Replica last offset: 6500
Backlog window:      5000 → 9000 (current)

6500 is within window → stream delta 6500→9000 only → partial sync ✓
KEY CONDITION

If the replica's last offset falls before the oldest entry still in the ring buffer, the data it needs is gone — overwritten by newer writes, and a full sync is the only option. If the offset is within the backlog window, only the delta streams.

Backlog size — an operational concern

If a write-heavy primary sees even a brief replica disconnect, the backlog can fill and overwrite old offsets — forcing an expensive full sync. Tuning repl-backlog-size to cover the expected disconnection window × write throughput is a real production concern. Getting it wrong turns routine network blips into repeated full syncs.

Replication ID change on failover

When a replica is promoted to primary (via Sentinel failover), it gets a new replication ID. Replicas following the old primary now have a mismatched ID and must full sync against the new primary. Redis 4+ addresses this with a secondary replication ID — the new primary remembers its old ID for a window, letting already-caught-up replicas partial sync even after a failover.

s8. Sentinel — Automated Failover

Replication alone gives a hot standby, but not automatic failover — if the primary dies, someone has to manually promote a replica. Sentinel is a separate process that monitors your Redis topology and acts on failures.

Sentinel 1 ─┐
Sentinel 2 ─┼──► monitors ──► Primary + Replicas
Sentinel 3 ─┘

Quorum — Why Odd Numbers

A single sentinel declaring the primary down isn't enough — a configurable quorum of sentinels must agree before failover triggers, preventing false positives from one sentinel losing network visibility. Always run 3 or 5 sentinels, never 2: with 2, one failing leaves you deadlocked with no majority; with 3, one can die and you still have quorum.

3 sentinels, quorum = 2

Sentinel 1: primary is down ─┐
Sentinel 2: primary is down ─┴── quorum reached → start failover
Sentinel 3: unreachable         (not needed)

Failover Sequence

StepWhat happens
1. SDOWNA sentinel stops getting responses — marks the primary subjectively down
2. ODOWNSentinels gossip, quorum agrees — marked objectively down
3. Leader electionSentinels elect a leader among themselves (Raft-like vote)
4. Replica selectionThe leader picks the most caught-up replica by replication offset
5. PromotionSends REPLICAOF NO ONE to promote it to primary
6. ReconfigurationOther replicas are told to follow the new primary
7. Client updateSentinel updates service discovery so clients find the new primary
CLIENT PATTERN — DON'T HARDCODE THE PRIMARY ADDRESS

During failover, there's a window where the topology is in flux — clients that cached the old primary address will fail. The correct pattern is a Sentinel-aware client that queries Sentinel for the current primary address on each new connection, never hardcoding the primary IP. Sentinel is not a proxy — it doesn't sit in the data path. It only manages topology and tells clients where the primary is; the client still connects directly to Redis.

s9. Redis Cluster & Hash Slots

Single-node Redis (even with Sentinel) is bounded by one machine's RAM and write throughput. Cluster breaks the dataset across multiple primary nodes — horizontal sharding with built-in replication and failover.

Hash Slot Partitioning

Redis Cluster uses 16384 hash slots. Every key maps to exactly one slot via CRC16(key) % 16384, and slots are distributed across primary nodes.

Node A  →  slots 0     – 5460
Node B  →  slots 5461  – 10922
Node C  →  slots 10923 – 16383

Every node knows the full slot map. If a client hits the wrong node, it gets a MOVED redirect pointing to the correct node — smart cluster clients cache the slot map locally and route correctly on the first attempt.

Client → SET user:42 "alice" → Node A
Node A computes slot 7423 → owned by Node B
Node A replies: MOVED 7423 node-b:6379
Client retries directly against Node B

Why 16384 slots specifically

Cluster nodes gossip constantly — heartbeat messages include the sender's slot map as a bitmap, so every node stays aware of the full topology.

16384 slots → 16384 bits → 2048 bytes → 2KB per heartbeat
65536 slots → 65536 bits → 8192 bytes → 8KB per heartbeat

16384 was the sweet spot — enough slots for granular distribution across thousands of nodes, small enough to gossip cheaply. Even with 1000 nodes, that's ~16 slots per node, plenty of resharding granularity.

Built-In Replication — No Sentinel Needed

Each primary shard has one or more replicas. Sentinel isn't used — cluster nodes monitor each other directly via peer-to-peer gossip on the cluster bus (port +10000). When enough nodes agree a primary is unreachable, the cluster promotes its replica automatically — same quorum principle, different actors.

Primary A  ←→  Replica A
Primary B  ←→  Replica B       ← minimum production setup: 3+3 nodes
Primary C  ←→  Replica C
SetupWho votesMinimum nodes
SentinelExternal Sentinel processes3 Sentinels + primary + replicas
ClusterPrimary nodes themselves3 primaries + 3 replicas

Multi-Key Operations — What Breaks

Any operation touching multiple keys only works if every key maps to the same slot. Redis cannot coordinate a single atomic operation across multiple nodes.

MSET user:1 "alice"  user:2 "bob"

CRC16("user:1") % 16384 → slot 5474 → Node B
CRC16("user:3") % 16384 → slot 1625 → Node A  ← different node

→ ERROR: CROSSSLOT keys not in same slot
CaseResult
All keys → same nodeWorks, fully atomic
Keys → different nodesCROSSSLOT error
Keys → mid-migration slotASK redirect (temporary)

Hash tags — forcing co-location

Wrap a substring in {} and Redis only hashes the part inside the braces, forcing related keys onto the same slot.

user:{42}:profile   →  CRC16("42") % 16384  ─┐
user:{42}:settings  →  CRC16("42") % 16384  ─┼── same slot, same node ✓
user:{42}:sessions  →  CRC16("42") % 16384  ─┘
HOT SLOT RISK

Co-locating keys intentionally means one entity's data all lands on one node. If that entity dominates traffic, one node bears disproportionate load — undermining the distribution benefit. Design hash tags carefully.

Resharding — MOVED vs. ASK

Adding or removing nodes requires slots to migrate — Redis does this live, without downtime. During migration, a slot is in transition and clients get two different redirects:

MOVED  →  slot permanently lives here now, update your slot map cache
ASK    →  slot is mid-migration, try this node just for this one request
KEY DESIGN SHIFT

Single-node Redis never required thinking about where a key lives. Cluster makes locality a first-class design concern — which keys need to be co-located for multi-key operations (use hash tags), and which are genuinely independent (let them distribute naturally). Design keys around access patterns, not just naming conventions.

Module IV — Operating Redis

s10. Eviction Policies

Redis is bounded by the machine's RAM. Once usage crosses maxmemory, every new write triggers an eviction attempt before the write is accepted. If Redis can't free memory, it rejects writes with an OOM error while still serving reads.

The Eight Policies

ScopePolicyWhat it evicts
No evictionnoevictionRejects writes. Never evicts.
TTL keys onlyvolatile-lruLRU among keys with a TTL set
volatile-lfuLFU among keys with a TTL set
volatile-ttlSoonest-to-expire among TTL keys
volatile-randomRandom among keys with a TTL set
All keysallkeys-lruLRU across the entire keyspace
allkeys-lfuLFU across the entire keyspace
allkeys-randomRandom across the entire keyspace

LRU vs. LFU

LRU (least recently used) tracks last_access_time per key and evicts the oldest timestamp — no concept of how often a key was accessed, only when it was last touched. LFU (least frequently used) tracks an access counter with time decay — the counter decays if a key isn't accessed, so old frequency doesn't count forever, making it reflect recent relevance rather than lifetime total.

Key A   accessed 1000x last month, 0x this week
Key B   accessed 50x this week

LRU → evicts A (oldest last_access_time)
LFU → evicts A (counter decayed, low recent frequency)

LRU asks: when did you last show up? LFU asks: how often have you been showing up lately? LRU struggles with scan patterns — a one-time bulk read of cold keys updates their timestamps, potentially evicting genuinely hot keys. LFU is immune, since a single access barely moves the frequency counter.

Approximate LRU — not exact

True LRU needs a global ordered structure tracking access time for every key — expensive at Redis's scale. Redis instead samples a random subset of keys (default 5, tunable via maxmemory-samples) and evicts the least recently used among that sample.

Full keyspace: millions of keys
                    │
                    ▼
Sample 5 random keys → evict the LRU among those 5

Not exact — the globally least-recently-used key may not be in the sample. Increasing maxmemory-samples improves accuracy at the cost of CPU per eviction.

Policy Selection Guide

Use caseRecommended policy
Pure cache, all keys disposableallkeys-lru or allkeys-lfu
Mix of persistent + cached keysvolatile-lru (only evict TTL keys)
Keys have meaningful TTLsvolatile-ttl
Never lose data silentlynoeviction (handle OOM in app)
Hot keys accessed repeatedly, long-termallkeys-lfu

TTL Expiry — Distinct from Eviction

Eviction is memory-pressure driven. TTL expiry is time-driven — Redis proactively removes keys whose time has passed via two mechanisms running in parallel.

MechanismHow it worksTradeoff
Lazy expiryKey checked on access — deleted if expiredZero background cost, but expired keys linger until touched
Active expiryBackground job periodically samples TTL keys, deletes expired onesReclaims memory even for keys never accessed again

s11. Quorum & Distributed Systems

Quorum isn't Redis-specific — it's a fundamental principle in any distributed system that needs to make a collective decision: leader election, failover, write acknowledgement. Once the mental model clicks, it surfaces everywhere.

The Universal Rule

Total nodes      = N
Quorum           = N/2 + 1  (strict majority)
Fault tolerance  = N/2      (nodes that can fail while the system stays alive)
NodesQuorum neededCan tolerateNote
220 failuresUseless for HA
321 failureMinimum viable
431 failureSame as 3, one node wasted
532 failuresRecommended for critical systems

Always deploy odd numbers. Even numbers give no extra fault tolerance but cost more — 4 nodes tolerates the same 1 failure as 3.

Odd Nodes Solve Split Brain

Split brain is what happens when a network partition causes two halves of a cluster to each think they're the primary, and independently accept writes — data diverges with no way to reconcile. Quorum prevents this, but only odd node counts guarantee it cleanly.

5 nodes, network partition

Side A: 3 nodes → strict majority of 5 → elects leader ✓
Side B: 2 nodes → minority → refuses to elect, goes silent ✓

One leader. Split brain impossible.
4 nodes, network partition

Side A: 2 nodes → 2/4, not majority → can't elect
Side B: 2 nodes → 2/4, not majority → can't elect

Both sides halt. No leader. Cluster unavailable.

Odd nodes guarantee that any partition always produces one side with strict majority — that side safely elects, the other stays silent. Even nodes can produce a symmetric 50/50 partition with no majority anywhere, leading to full halt or split brain depending on the implementation.

HALTING IS SAFER THAN DIVERGING

A cluster refusing to elect a leader means downtime — recoverable. Two leaders accepting conflicting writes means data corruption — often unrecoverable. Quorum enforces the safer failure mode.

Where Quorum Appears Across Systems

SystemQuorum used for
Redis SentinelSentinel processes voting to declare a primary ODOWN
Redis ClusterPrimary nodes voting to declare a shard primary FAIL
etcd / ZooKeeperDistributed coordination — Kubernetes' control plane uses etcd with a minimum of 3 nodes
Kafka ISRA write commits only once enough in-sync replicas confirm it
Cosmos DBWrite acknowledged after a quorum of regional replicas confirm — consistency levels tune how strict this is
SQL Server Always OnAutomatic failover requires quorum of availability-group members plus a witness node

CAP Theorem Connection

During a network partition, a system must choose between two guarantees — it can't have both at once.

ChoiceBehaviorExamples
CP — Consistent + Partition-tolerantRefuses writes until quorum is reachable. Downtime over divergence.Redis Cluster, etcd, Cosmos strong consistency
AP — Available + Partition-tolerantAccepts writes on both sides, reconciles later. Divergence over downtime.Cosmos eventual consistency, DynamoDB
NEITHER IS WRONG

CP vs. AP is a business decision — can your system tolerate data divergence, or downtime? Financial systems typically choose CP. High-availability, read-heavy systems often choose AP. The right answer depends on which failure mode hurts your users less.

s12. Operations & Sizing

Redis's memory usage is larger than your raw dataset. Several additional regions need headroom — ignoring them is the most common cause of OOM crashes in production.

Memory Breakdown

RegionSize estimateNotes
Dataset footprintRaw data × 1.5–3xjemalloc rounding, per-key overhead (~50–70 bytes), encoding overhead after listpack promotion
Fork headroomUp to 1× datasetRDB snapshot and AOF rewrite both fork. Write-heavy workloads cause the OS to copy modified pages — RAM can temporarily double
AOF rewrite bufferWrite rate × rewrite durationNew writes buffered in RAM during the rewrite window. 100MB/s × 30s rewrite ≈ 3GB
Client buffersConnections × buffer sizeTypically small — pathological with slow clients, each can hold up to a 1GB output buffer
OS + kernel~1–2GBPage cache, kernel structures, other processes

Practical Sizing Formula

(dataset × 1.5) × 2 + 2GB

Example: 4GB raw data
  4GB × 1.5 = 6GB   dataset footprint
  6GB × 2   = 12GB  fork headroom
            + 2GB   OS + buffers
            ──────
            14GB  → provision a 16GB node

Key Rules

RuleWhy
Never provision less than 2× datasetFork can double RAM usage temporarily
Write-heavy workloads → 3× datasetMore pages copied during the fork window
Set maxmemory to ~70% of total RAMLeaves headroom for a fork spike above the dataset cap
Monitor used_memory_rss, not used_memoryRSS is what the OS actually allocated — includes fragmentation
mem_fragmentation_ratio > 1.5jemalloc holding freed pages — real RAM pressure is higher than used_memory shows
FORK IS THE DANGEROUS ONE

RDB snapshots and AOF rewrite both call fork(). On write-heavy workloads, the OS copies every modified 4KB page during the fork window — RAM usage can spike to 2× dataset size instantly. Sizing for the dataset alone, and ignoring fork headroom, is the most common cause of OOM crashes in production Redis.
